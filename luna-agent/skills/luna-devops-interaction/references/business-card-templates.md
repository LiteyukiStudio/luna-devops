# 业务卡片模板命中规则

业务卡片模板把高频交互固化为稳定参数契约。调用 `create_interaction_cards` 时，优先只提供
`schemaVersion`、`generationId` 和 `businessTemplate`。平台会把业务模板编译为受控通用卡片，
前端仍使用同一套渲染、校验、权限和提交链路。

## 选择顺序

依次回答四个问题：

1. 当前是否正在等待用户输入？等待输入只能选交互模板。
2. 当前是候选选择、参数收集、变更核对、诊断、进度、结果还是健康概览？
3. 候选数量是多少？2～5 个丰富候选与 6～50 个候选使用不同模板。
4. 模板能否表达全部必要信息？能表达就不得改用通用卡片自绘。

不要按“数据库”“应用”“网关”等资源名选择模板。同一个 PostgreSQL 工作流可以依次命中
`candidate_picker`、`resource_configuration`、`change_review`、`execution_progress` 和
`operation_result`；模板描述的是当前阶段，不是资源类型。

## 命中表

| `templateId` | 必须命中的情形 | 不应命中的情形 |
| --- | --- | --- |
| `candidate_picker` | 已取得 2～5 个真实候选；每项需要名称以外的说明；必须让用户选择一个才能继续 | 只有轻量文字建议；候选超过 5 个；只是展示搜索结果而不等待选择 |
| `candidate_select` | 已取得 6～50 个可信候选；只需从中选择一个；候选可用简短 label/description 表达 | 候选需要逐项复杂对比；候选不到 6 个；候选尚未从工具取得 |
| `resource_configuration` | 已知操作目标，需要收集一个或多个结构化参数；适用于创建、安装、部署、构建、网关、运行配置等 | 参数已经完整且只需核对；只缺自然语言澄清；仅展示资源事实 |
| `change_review` | 写操作参数已完整，执行前需要集中展示目标、参数、影响或风险，并提供继续动作 | 平台高风险批准卡；仍缺参数；操作已经执行完成 |
| `diagnosis_report` | 已完成检查，能够给出结论、分项状态和可核对证据 | 仍在查询；只展示普通资源详情；把未经验证的猜测当结论 |
| `execution_progress` | 构建、部署、发布、迁移或批量任务仍在运行；需要展示总进度和步骤状态 | 任务已经终止；只收到请求受理但没有任何可读取进度；用进度卡假装持续轮询 |
| `operation_result` | 操作达到可验证终态，需要展示成功、部分成功或失败及关键事实 | 仅提交、排队或运行中；卡片生成完成但业务未完成；没有回读证据却声称成功 |
| `health_overview` | 已取得一组实时指标和分项健康状态，需要帮助用户判断优先级 | 查看单个资源详情；诊断具体故障原因；指标来自旧缓存或猜测 |

## 交互模板

### candidate_picker

每个 `candidates` 元素会生成独立候选卡。`selectionLabel` 使用用户当前语言描述动作；
`selectionMessage` 必须明确回答当前问题，并携带可信候选的名称或 ID；不要写成“继续”
“选这个”等失去上下文的消息。

适用例：

- 在应用市场模板、镜像和源码三种来源中选择部署来源。
- 在 3 个项目空间中选择目标空间。
- 在 2 个可用集群中选择发布目标。

反例：搜索得到 19 个模板后生成 19 张卡。此时使用 `candidate_select`，或者先按用户意图筛选。

### candidate_select

候选必须来自同一类可信资源。`submitLabel` 使用用户当前语言；`submitMessage` 必须包含
`{{candidate}}`，这样用户选择的值才能安全带回下一轮。label 面向用户，value 使用真实稳定 ID。

适用例：从 11 个项目空间、19 个应用模板或多个镜像 Tag 中选一个。

反例：把项目空间、集群和模板混进同一个 select。它们属于不同决策，应分阶段处理。

### resource_configuration

用于收集当前动作真正缺少的参数。`facts` 展示已确定且不需要修改的目标事实；`sections`
只包含用户仍需填写或选择的字段。可发现的资源必须做成 select，不让用户手填 ID。

- 一组彼此独立字段使用一个 section。
- 字段较多时按“目标 / 构建 / 运行 / 访问”分 section，但仍在一轮表单中提交。
- 非敏感字段可用 `send_message` 和 `{{field_id}}` 进入下一轮。
- 参数已完整且写工具可用时，使用 `tool` submit 和 JSON Pointer binding。
- Secret 不得插入消息。遵循平台受控 Secret 提交流程，不把密钥写进对话。

适用例：

- 安装模板时填写应用名、数据库名、资源规格和项目空间。
- 源码部署时选择仓库、分支、Dockerfile、构建上下文和端口。
- 配置网关时填写域名、路径、服务端口和 TLS 策略。

反例：参数都已完整，却再次让用户填写；此时改用 `change_review` 或直接执行低风险工具。

### change_review

这是业务参数核对卡，不是平台批准卡。它可以触发真实 tool action，但平台仍会在必要时生成
独立的批准 / MFA 界面。`changes` 使用稳定标签展示最终参数；`risks` 只写已验证的风险或检查项。

适用例：发布新镜像前核对应用、环境、镜像 Tag、副本数和影响；修改网关前核对域名与路由。

反例：写“已批准”“安全检查已通过”，但没有对应工具证据。

## 展示模板

### diagnosis_report

先在 `conclusion` 给出直接结论，再用 `findings` 区分成功、警告和错误，最后把日志摘要、事件、
请求编号或资源状态放进 `evidence`。未知原因应明确标记未知，不能推断为权限或网络问题。

### execution_progress

能计算比例时使用 `determinate` 并提供 `value`；不能计算时使用 `indeterminate`。`steps` 至少
包含当前步骤，并准确区分 pending、running、success、warning、error 和 skipped。达到终态后
重新生成 `operation_result`，不要继续显示运行中卡片。

### operation_result

`outcome` 反映已验证终态。成功需要写工具结果和权威回读；部分成功使用 warning，并在 steps
中列出失败项；失败使用 error，并给出稳定、可纠正的原因。请求受理、排队和运行中不得命中。

### health_overview

`metrics` 只保留帮助判断健康和优先级的 1～6 项指标，`statuses` 给出各子系统的实时状态。
普通零值可中性展示，异常零值必须使用 warning/error 并说明影响。上游不可达时显示不可用，
不能沿用上一次成功值。

## 何时使用通用卡片兜底

只有下列必要结构无法由业务模板表达时，才直接提供 `mode/template/cards`：

- 需要同维度宽表格比较，并且候选卡无法清晰表达。
- 需要代码、Diff、关系图、时间线、图表或资源链接。
- 同一阶段需要特殊的多卡组合，且拆成连续业务模板会损失语义。
- 需要条件字段 `visibleWhen`，业务配置模板目前无法表达字段依赖。

兜底不等于任意绘制。仍只能使用已注册内容块、字段和动作，不得输出 HTML、CSS 或脚本。

## 完整工作流示例

用户要求“把仓库部署成一个应用”时：

1. 读取项目空间、代码账户和仓库事实。
2. 有 2～5 个仓库候选时用 `candidate_picker`；候选更多时用 `candidate_select`。
3. 读取 README 和构建信息后，用 `resource_configuration` 收集无法发现的参数。
4. 参数完整且需要用户核对时用 `change_review`，随后调用真实写工具。
5. 构建或发布仍在运行时用 `execution_progress`，并继续读取状态。
6. 运行资源和健康检查达到终态后用 `operation_result`。

不得从第 2 步直接生成成功回执，也不得把第 3 步替换为“前往应用页面”的导航。
