## 确定目标与完成条件

先区分用户只要求诊断，还是要求诊断并修复。只诊断时不得擅自写入；要求修复时也必须先
取得足以支持变更的证据。

优先从当前页面、会话和平台工具发现项目空间、应用、部署目标、环境和最近 Release。只询问
工具无法获得的用户观察，例如现象、影响范围和大致开始时间；不要让用户重复提供资源 ID。
存在多个可信目标时使用资源选择卡片。开始取证前明确用户可观察的完成条件，例如恢复就绪、
接口成功、错误率下降或公网入口可访问。

## 识别故障入口

先把现象归入最接近的一类，再选择取证路径：

| 入口 | 首要问题 |
| --- | --- |
| 从未成功交付 | 是否完成来源配置、构建、制品和首个 Release |
| 最近发布后失败 | 新 Revision 在构建、发布、调度、启动或健康检查的哪个边界失败 |
| 原本正常后异常 | 故障窗口内是否有发布、配置、依赖、容量或平台变化 |
| 仅入口不可达 | 应用进程、Service Endpoint、Route、DNS、TLS 中最早异常的是哪一层 |
| 性能下降或间歇异常 | 是否集中在特定副本、请求、时间段、依赖或资源饱和状态 |
| 依赖访问失败 | 服务引用、地址、端口、认证、网络、隔离单元和目标依赖健康是否一致 |
| 多应用同时异常 | 是否存在共享依赖、集群、网关、Provider 或平台级故障 |

用户描述可能同时命中多个入口。此时先用最少读取区分分支，不要一次拉取所有日志和平台资源。

## 建立统一取证窗口

所有状态、事件、日志、指标和 Trace 使用同一故障窗口。优先采用用户给出的发生时间；没有时，
以最后一次 Release、配置变更或首个异常事件为锚点，并保留少量前置时间作为基线。记录时间区间、
时区、Release/Revision 和相关请求或 Trace 标识，避免把无关旧错误当作当前根因。

实时状态与历史证据必须分开：当前 Ready 不证明故障窗口内正常，历史失败也不证明当前仍失败。
上游不可达或观察结果为 `unavailable` 时，明确说明观测缺口，不使用数据库旧状态替代实时事实。

## 沿最短路径定位首个异常边界

先读取应用拓扑、部署目标、当前与最近成功 Release、工作负载摘要、近期事件和服务关系，再按入口
进入最短分支：

1. **没有可运行 Release**：检查来源、构建配置、BuildRun、BuildJob、制品 Tag/Digest 和 Release
   是否真实创建。构建失败时只读取对应 Job 日志和事件，不提前检查网关。
2. **Release 或 Rollout 失败**：核对期望 Revision、镜像、配置、Secret 引用、部署日志、集群连接、
   调度和 Rollout 条件。Release 记录存在不等于工作负载已经更新。
3. **Pod 未就绪或反复重启**：检查调度、镜像拉取、卷挂载、初始化、探针、退出码、OOM、资源限制
   和容器日志。多副本时比较异常副本与健康副本，并标明 Pod、容器、Revision 和时间范围。
4. **Service 无 Endpoint**：检查 selector、目标 Pod Ready、命名端口和容器端口；不能只因 Service
   对象存在就判断链路正常。
5. **依赖访问失败**：读取服务引用和拓扑，沿源部署目标到目标部署目标检查地址、端口、Endpoint、
   NetworkPolicy、TLS、凭据引用、隔离单元和目标依赖健康。遵守
   `service-dependency-planning.md` 中对应组件的隔离与复用规则。
6. **网关或公网异常**：先确认应用与 Service 在集群内可用，再检查 Route 条件、后端引用、DNS、
   TLS 和实际外部响应；不要用重建网关掩盖应用自身故障。
7. **性能或间歇故障**：比较副本、Revision 和依赖维度的延迟、错误、CPU、内存、重启和连接状态，
   再读取同一窗口内的日志或 Trace。避免用单条慢请求推断整体性能。

日志和终端不是默认第一步。优先使用结构化状态、事件和受控日志工具；只有平台没有等价业务工具且
确实需要进程内证据时才使用受控终端，并且不得通过终端直接修改资源绕过平台操作、审计和批准。

## 使用一次性运行命令

只有平台没有等价结构化读取工具且确实需要容器内证据时，才调用 `execReleaseRuntimeCommand`。

1. 先从可信工具结果确定唯一的项目空间、Release、部署配置和容器；存在多个容器时先让用户选择。
2. 每次只提交一条独立、范围明确、输出有限的命令，并等待当前参数的单次批准；不得把一次批准视为
   后续命令授权。
3. 多条诊断命令必须分别调用，不能假设工作目录、环境变量、Shell 选项或进程状态会跨调用保留。
   需要相同上下文时，在每条命令参数中显式、最小地重建它。
4. 不要启动交互程序、后台常驻进程或无限输出命令。命令超时或输出过大时应缩小查询范围，不要重复
   拉取全部输出。

命令内容、标准输出和错误输出可能包含敏感数据。不得读取或回显 Secret、Token、Cookie、连接串，
也不得用终端绕过已有平台写工具。需要修改部署、配置、网关或运行态资源时，应调用
对应平台注册工具，使批准、审计、幂等和验收保持完整。

## 区分症状与根因

结论必须分为四层：

- **症状**：用户和平台观察到的异常，例如 Pod 不就绪或接口超时。
- **直接原因**：直接导致症状的失败，例如健康检查返回 500。
- **根因**：导致直接原因的最早可纠正事实，例如数据库迁移未执行。
- **待验证假设**：当前证据不能确认的候选原因，以及能区分它的下一项检查。

只有证据闭合时才声明根因。多个错误同时存在时按时间和依赖关系找第一个失败边界，不把最后出现的
报错自动当作根因。诊断卡先给影响和结论，再给时间窗口、证据链与最高收益的下一步。

## 执行可回滚修复

用户要求修复且根因明确时，选择作用范围最小、可审计、可回滚的平台注册操作：

1. 回读并保存将要修改的当前配置、Revision 或资源引用，明确影响的应用、环境和依赖。
2. 校验目标仍与取证时一致；状态已经变化时重新诊断，不能按陈旧证据执行。
3. 需要批准的变更交给平台逐次参数绑定流程，不额外用文字重复确认。
4. 配置变化通过部署目标或配置接口完成，并按平台语义创建新 Release；不要直接修改运行中 Pod。
5. 重启只用于配置已经正确但进程需要重建的情况；未知根因时不得把重启当作修复。
6. 回滚必须选择真实历史成功 Revision，并说明会恢复哪些镜像与配置、不会恢复哪些外部数据。

一次只实施能验证主要假设的最小变更。修复失败时保留失败记录，使用保存的配置或历史成功 Revision
恢复；不得连续叠加多个未验证变更。

## 沿原路径验收

修复后沿诊断时的同一观察链重新读取，避免换一套较宽松的成功标准：

- 目标 Release/Revision 与计划一致并达到成功终态。
- 所有预期副本就绪，旧异常副本已经退出，Rollout 不再进行中。
- Service 存在预期 Endpoint，端口与探针一致。
- 关键依赖边的地址、认证、网络和应用侧连接恢复。
- 用户要求公网访问时，Route、DNS、TLS 与真实外部响应同时满足目标。
- 在与故障频率相称的观察窗口内，没有同类事件、重启或错误再次出现。

间歇故障不能因一次成功请求就判定修复完成。无法等待足够窗口时，只能说明“当前已恢复，仍需观察”，
并给出具体观察项和期限。

## 准确结束任务

- **已诊断**：具有时间一致、相互关联的证据链，明确症状、直接原因、根因和优先修复项。
- **已修复**：写操作成功且沿原观察链完成验收。
- **进行中**：构建、Release、Rollout、恢复或观察窗口尚未结束。
- **等待输入/批准**：只说明等待的具体内容，不把卡片生成当作业务完成。
- **尚未定位**：列出已排除项、剩余假设和下一条能区分假设的检查。
- **阻塞**：说明缺少的权限、工具、观测数据或上游可用性，以及不会冒险执行的原因。

无论哪种终态，都保留稳定错误码、请求 ID、Trace ID、资源 ID 和关键时间，但对日志、配置和第三方
响应做安全摘要，不暴露 Secret、Token、Cookie、连接串或用户敏感数据。
