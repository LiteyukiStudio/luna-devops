# Luna DevOps 产品与一体化方案

本文记录产品定位与一体化方案的核心决策。已实现的具体页面、数据对象字段、MVP 里程碑
与迭代过程以代码和 TODO 为准，本文不再逐项罗列。

## 1. 产品定位

Luna DevOps 是面向个人开发者和小团队的轻量级应用交付平台，把代码仓库、CI、镜像仓库、
运行环境、网关和域名打通。

一句话：**开发者只需维护代码、Dockerfile 和少量配置，平台负责构建镜像、部署应用、
配置网关并分配访问域名。**

平台定位为统一的 DevOps 应用交付控制平面——不替代 GitHub、Gitea、Harbor、DockerHub、
Kubernetes、K3s、Ingress 等成熟组件，而是将它们抽象、编排、打通，提供一致的交付体验。

## 2. 产品原则

- **简单优先**：单个开发者也能理解和使用；优先把主流程跑通，不做过度抽象。
- **显式可见**：平台生成的构建记录、镜像、部署资源和域名都可查看。
- **受控默认**：高风险操作有确认、审批和审计，不替用户做不可逆决定。

## 3. 一体化关键边界

平台应该做：统一入口、统一资源抽象、统一权限、统一发布流程、统一状态展示、统一审计。

平台不应该做（边界）：

- GitHub/Gitea 只作为代码源、授权源和 Webhook 来源，不作为构建执行器。
- 不重复造已有成熟组件（镜像仓库、K8s、网关）的轮子，只做编排与抽象。
- 构建 Job 不挂载宿主机 Docker socket、不默认 privileged，构建网络默认受限出站。

## 4. 推荐默认技术路线

| 能力 | 推荐组件 |
| --- | --- |
| 统一认证 | 后台配置的 OIDC Provider（Casdoor 等） |
| 代码库 | Gitea + GitHub |
| 构建 | Worker 调度 + Kubernetes Job + BuildKit rootless |
| 镜像仓库 | Harbor |
| 运行环境 | Kubernetes / K3s |
| 网关 | Gateway API / Ingress |

## 5. 用户角色与交付流程（摘要）

- 角色分为平台管理员、项目空间 Owner/Admin/Developer/Viewer 等。`internal/authz` 唯一定义项目
  Action 到角色的 RBAC 策略。第一方 Luna CLI 登录直接继承当前用户权限，不暴露额外 Scope；个人令牌、
  第三方 OAuth 应用与 Agent 服务身份仍按 OpenAPI 凭证 Scope 限权。前端只消费共享角色枚举和稳定拒绝码，
  不维护可放行操作的副本。
- 核心交付路径：连接代码源 → 构建镜像（或直用已有镜像/模板）→ 创建部署配置 → 发布 Release →
  配置网关与域名 → 观察运行状态与诊断。
- 三类交付来源：应用市场模板、已有镜像、代码仓库构建。

## 6. 运行观察与计费口径

- `DeploymentTarget.Replicas` 只表达用户配置的基准副本数；Kubernetes workload 的
  `desired/updated/ready/available` 副本分别表达实时期望、发布进度、就绪和可用状态。
- 实时容量必须来自同一次 Kubernetes 观察。上游不可达时返回 `unavailable`，不得用数据库配置、
  Redis、进程缓存或上一次响应伪装当前状态。
- RuntimeCluster 保存 CPU request、内存 request、CPU limit、内存 limit 四个 0–100 百分比；默认
  `10/25/100/100`。应用只保存每副本 CPU、内存配额，Worker 在渲染时通过统一资源策略组件生成
  Kubernetes requests/limits；0 表示省略字段，策略更新只影响后续重新部署。
- 运行计费只读取分钟级不可变 `runtime_observations`，并以 `(deployment_target_id, period_start)`
  保证幂等。每个自然分钟记录当时的有效 request、期望副本、`metrics.k8s.io` 实际 CPU/内存和策略
  快照；期望副本为 `0` 是合法零用量，缺失分钟不插值或外推。
- 结算仍以自然小时为粒度。CPU 与内存分别在每个采样区间计算
  `max(有效 request × 期望副本, 实际用量) × 有效时长` 后求和；指标不可用但工作负载已确认运行时
  只使用 request floor，request 为 0 时不估算。历史观察和已结算账单不可修改。
