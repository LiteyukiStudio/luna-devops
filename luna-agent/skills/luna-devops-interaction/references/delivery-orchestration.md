## 先定义交付目标

将“部署一个应用”拆成以下阶段，按顺序推进并记录当前阶段：

1. 确认或创建目标项目空间。
2. 发现并确认交付来源：应用市场模板、已有镜像或代码仓库。
3. 取得来源事实并收集仍缺少的参数。
4. 创建或复用应用。
5. 创建部署配置，并绑定来源、运行集群和运行参数。
6. 源码路径先构建镜像；模板或已有镜像路径直接准备 Release。
7. 创建 Release 并观察部署状态。
8. 回读应用、部署配置、Release 和工作负载，按目标验收。
9. 用户需要公网访问时，再配置并验证访问入口。

不得跳过中间阶段并用计划、确认卡或参数摘要冒充执行结果。用户没有要求公网访问时，
应用运行就绪可以作为交付终点；用户要求可访问 URL 时，网关验收也是必需项。

## 规划服务与依赖

创建应用前先建立服务拓扑，区分可独立发布的业务服务、有状态依赖、共享平台能力、一次性
任务和外部托管服务。不同 Dockerfile、镜像、生命周期、端口、扩缩容、发布或故障恢复
边界的组件应拆成独立应用；迁移和初始化等一次性步骤优先归属发布流程。

数据库、缓存、队列、对象存储、搜索、向量库、可观测、网关和身份服务不得统一套用“全部
新建”或“看到现有就复用”。按根 Skill 直接索引的 `service-dependency-planning.md` 判断
所有权、隔离、生命周期、兼容性、容量、故障域、连通性和删除语义，再选择复用现有实例、
创建解决方案私有依赖、创建服务专用依赖或绑定外部服务。存在实质权衡时用交互卡片确认。

## 确认项目空间

- 先列出用户可用项目空间，并优先复用用户明确指定或当前页面中的可信目标。
- 按根 Skill 直接索引的 `resource-resolution.md` 过滤可写候选。只有一个有效项目空间时
  直接采用；多个且没有可信目标时才生成选择交互。用户明确要求新建或更换时不得自动采用。
- 让用户从多个项目空间中选择时，除现有候选外必须提供“新建项目空间”入口
  （`candidate_picker` / `candidate_select` 的 `creationAction`）；用户选择新建后，
  收集名称和标识符并调用创建工具，回读取得真实 ID 后继续后续创建应用，
  不让用户重新走一遍流程。找不到目标且没有创建能力时，才只展示现有候选。
- 用户明确要新建时，收集名称和标识符并调用已注册的创建工具。
- 创建成功后回读项目空间，取得真实 ID，再继续创建应用。项目空间卡片或创建请求被
  受理不等于项目空间已经可用。
- 创建应用前确认用户对目标项目空间拥有对应写权限；最终权限由业务 API 判断。

## 选择来源

用户未指定来源时，使用交互卡片提供三个有意义的选择，并说明差异：

| 来源 | 适用情况 | 后续主要步骤 |
| --- | --- | --- |
| 应用市场模板 | 数据库、缓存、消息队列、监控和常用自托管应用 | 读取模板参数 → 填表 → 安装 |
| 已有镜像 | 已有可拉取的 OCI 镜像，希望直接运行 | 选择镜像与 Tag/Digest → 配置运行参数 → Release |
| 代码仓库 | 需要平台从源码构建并持续交付 | 读取仓库与文档 → 配置构建 → BuildRun → Release |

新手模式（见根 Skill“识别并陪伴不熟悉部署的用户”）下，把上表翻译成小白能懂的表达，
每行加一句“选这个如果你…”：

| 新手版选项 | 选这个如果你… |
| --- | --- |
| 直接装现成的 | 想要数据库、缓存、博客、监控这类别人做好的应用，不想自己写代码 |
| 我已经有打包好的应用 | 已经有一个能打包容器镜像（或别人给过你镜像地址），想直接运行 |
| 从我的代码构建 | 手上有自己的项目代码（如 GitHub 仓库），想让平台帮你打包并上线 |

用户已经明确来源时直接采用。用户只给出 GitHub、官网或部署文档 URL 时，先按下节评估
官方镜像捷径；这是一项可回退的建议，不是强制要求，也不应阻止用户明确要求的源码构建。
其他来源仍无法从上下文确定时才让用户选择。不要同时询问三个分支的全部字段。

## 评估官方镜像捷径

用户给出仓库、官网或官方部署文档时，不要因为入口是代码链接就直接认定必须源码构建。
先读取当前版本的官方文档、Release、容器清单和自动化配置，识别项目是否发布 Docker Hub、
GHCR 或其他 OCI Registry 镜像。对每个可独立部署的服务分别评估。允许同一解决方案同时使用官方镜像和源码构建。

同时满足以下条件时，建议把官方镜像作为默认交付路径，并简要说明它可以减少构建时间和
构建配置；不要额外要求用户在等价来源之间选择：

- 镜像由项目官方组织或官方文档明确认可的发布方维护，镜像仓库与当前项目身份一致。
- 当前目标 Release、Tag 或 Commit 有对应的不可变 Tag/Digest；不得只凭 `latest` 判断版本。
- Registry 中能够发现该 Tag/Digest，目标集群架构存在对应 Manifest，且目标集群具备拉取能力。
- 当前文档仍推荐该镜像，仓库或镜像没有归档、废弃、EOL、长期停更或版本明显落后的证据。
- 镜像暴露的端口、启动方式、配置、迁移和持久化能力能够满足用户目标，不需要修改源码或
  注入只能在构建期完成的定制。

只要关键条件无法验证，就把镜像标记为候选而不是事实；存在实质权衡时再用交互卡片说明
依据并让用户选择。以下情况直接回退到代码仓库分支：找不到官方镜像或目标版本、镜像不可
拉取、架构不兼容、官方已废弃或明显落后、文档与镜像行为冲突、需要源码修改/自定义构建，
或镜像缺少完成目标所需能力。回退时保留已经确认的服务拓扑和运行参数，不要从头重复取证。

## 应用市场模板分支

1. 使用 `listAppTemplates` 按关键词和分类发现候选摘要（不含完整参数定义）。
2. 安装意图下使用交互式候选卡；用户只是比较时使用展示式卡。
3. 用户选定模板后，用 `getAppTemplate` 读取该模板的真实参数、默认值、镜像、默认资源、数据卷和 Secret 生成策略。
4. 表单只覆盖资源解析后仍未确定的目标项目空间、集群，以及应用名称与标识符、模板
   必填参数和用户需要调整的镜像、CPU、内存、副本与容量；自动生成的 Secret 不要求
   用户在聊天中填写。
5. 参数齐全后调用真实安装工具。没有安装工具时明确停在能力阻塞，不能生成安装回执。
6. 回读新应用、部署配置和安装记录。立即部署时继续观察 Release 和工作负载。

验收：目标项目空间中存在来源模板、名称和配置符合预期的应用及部署配置；若用户要求
立即部署，Release 与工作负载必须达到就绪终态。

## 已有镜像分支

1. 发现用户可用镜像站、凭据、仓库和 Tag；优先使用 Digest 固定生产发布版本。
2. 用户提供完整镜像引用时仍应确认镜像站可访问、凭据范围和目标集群拉取能力；不要
   根据字符串存在就假定镜像可用。
3. 尽量在一张 `resource_configuration` 表单中收齐全部参数：项目空间、应用名称与标识符、
   镜像引用、环境阶段、服务端口、运行配置、数据卷和必要的非敏感环境变量；Secret 通过
   平台受控字段处理。只有确实需要用户决定时才询问目标集群（`clusterId` 为空即平台默认
   集群），不要因为表单里存在该字段就要求用户填写。
4. 参数齐全后在同一轮内连续执行：创建或复用应用 → 创建 `sourceType: image` 的部署配置
   → 创建 Release，不要在每步之间停下来等用户确认；只有缺少真实输入、等待批准/MFA
   或工具返回错误时才中断并说明。
5. 观察镜像拉取、Pod、Service 和健康探针。镜像记录创建成功不等于工作负载可运行。

验收：应用和部署配置属于正确项目空间，Release 使用预期 Tag/Digest，工作负载就绪且
服务端口存在；用户要求访问入口时还要完成网关验收。

## 代码仓库分支

具体仓库取证、README 复核、monorepo 拆分、迁移与多服务验收遵守根 Skill 直接索引的
`repository-delivery.md`；本节只定义交付编排阶段。

1. 优先发现已连接的 Git Provider、账号、仓库和分支。私有仓库使用平台 Git 能力，
   不使用公开网页工具绕过认证。
2. 用户提供公开 GitHub 或网页 URL 时先用 `fetchWebPage` 读取；只有名称时先
   `webSearch`，再读取官方仓库或官网。优先检查 README、部署文档、Dockerfile、
   Compose、包管理清单、`.env.example`、Helm Chart 和 Kubernetes 清单；若其中声明官方
   OCI 镜像，先回到“评估官方镜像捷径”，验证可用时转入已有镜像分支。
   新手模式且项目没有 Dockerfile 时，主动说明“你的项目没有 Docker 配置，我会用平台的
   默认模板帮你打包”，只确认项目类型、启动命令和端口，不要求用户编写或理解 Dockerfile。
3. 使用平台仓库工具读取分支、目录、Dockerfile 和构建选项。公开网络内容只能辅助
   理解，不替代平台仓库绑定和权限校验。
4. 把值分为三类：
   - 明确事实：仓库、分支、Dockerfile、构建上下文、启动命令和文档声明端口。
   - 可编辑推断：构建模板、工作目录、非敏感命令和资源建议。
   - 用户决策：项目空间、应用名、集群、域名、资源规格和 Secret。
5. 先按 `service-dependency-planning.md` 生成多服务与依赖计划，再用表单让用户确认分支、构建定义、Dockerfile、上下文、构建参数、输出镜像站、
   镜像命名、端口、运行配置和发布策略。monorepo 按服务创建多个应用或部署配置，
   不把不同 Dockerfile 强行合并为一个服务。
6. 创建或复用应用，建立仓库绑定与 Webhook，创建 `sourceType: repository` 的部署
   配置，然后触发 BuildRun。
7. BuildRun 成功并取得制品 Tag/Digest 后创建 Release。构建成功不等于部署成功。

验收：仓库绑定指向正确账号、仓库和版本；BuildRun 成功并产生预期制品；Release 使用
该制品；工作负载和服务就绪。启用自动化时还要验证 Webhook 和自动发布策略。

## 共享运行参数

只收集当前应用实际需要的字段，优先使用文档或模板事实作为可编辑默认值：

- 环境阶段、Deployment/StatefulSet、服务端口和副本数。目标集群默认留空（空表示平台默认集群），
  只有存在多个候选且必须由用户决定时才提供选择字段。
- CPU/内存 request 与 limit、健康探针、启动命令和镜像拉取策略。
- 非敏感环境变量、项目空间公共配置和部署级覆盖。
- Secret 引用、配置文件、密钥文件、数据卷和持久化策略。
- 环境变量值支持 `${VAR_NAME}` 引用同部署的其他变量（含 Secret），例如 `DATABASE_URL=postgresql://${USER}:${PASSWORD}@${HOST}:${PORT}/db`，渲染时自动展开。
- HPA、调度、安全上下文、initContainer、sidecar 和生命周期钩子等高级项。

不要在首次交付时一次询问所有高级 Kubernetes 字段。只有来源文档或用户目标要求时
才展开；其余使用平台安全默认值。

## 恢复与停止条件

- 缺少来源：回到来源选择，不创建空应用。
- 缺少项目空间：选择或创建后继续，不让用户手填不透明 ID。
- 来源读取失败：说明认证、网络、黑名单、分支或文件问题，并保留已经确认的参数。
- 构建失败：进入构建诊断，修正后创建新 BuildRun；不要直接进入 Release。
- 发布失败：读取发布、运行时事件与日志；修正配置后创建新 Release 或选择安全回滚。
- 长任务仍运行：报告任务 ID、当前阶段和“进行中”，不要占用模型循环反复无间隔轮询。
- 当前工具目录缺少下一写操作：明确“尚未执行”、缺失 operation 和可保留的已确认输入。
