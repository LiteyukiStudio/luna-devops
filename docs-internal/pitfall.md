# 踩坑记录

## 问题 1：被引用资源删除或收权后残留悬空 ID，导致下游配置无法编辑保存

### 复现方式

1. 下游对象（如通知规则、部署配置、集群出站例外、共享资源项目绑定）引用了某个上游资源 ID（如通知渠道、应用、部署配置、项目空间、代码仓库绑定、镜像站、构建变量集等）。
2. 将该上游资源软删除，或通过编辑接口将其从某项目空间的可用范围（`projectIds` / `scope`）中移除。
3. 重新打开下游对象的编辑弹窗并保存：
   - 前端表单直接从数据库历史字段初始化 ID 列表，但候选项只渲染当前存活/有权限的资源，用户无法在界面上看到或取消勾选已失效的旧 ID；
   - 提交时旧 ID 随新勾选的 ID 一起发给后端，后端对全部提交 ID 做存在性或绑定校验时报错拦截（如 `notification.channel_not_found`、`project not found`、`runtime_cluster.forbidden` 等）。

### 原因

1. **删除与收权路径缺少引用守卫或级联清理**：多数软删除接口（`.Delete()`）和作用域更新接口（`ReplaceScopedResourceProjectBindings`）只处理了自身记录，未检查或同步剥离下游 JSON 数组、逗号分隔字段、无外键关联列及绑定表中的历史引用。
2. **编辑路径与解绑路径校验不一致**：部分模块只在专门的 `unbind` 接口做了 `in_use` 检查，但允许通过 `PUT` 更新 `projectIds` 或 `scope` 直接绕过检查。
3. **前端编辑表单未过滤失效引用**：表单初始化和构造提交载荷时未按当前可用候选项过滤历史残留 ID，导致不可见的幽灵 ID 被原样回传。

### 解决方案

1. **后端写入口统一守卫或剥离**：
   - **强依赖引用**（如部署配置引用的代码仓库绑定、镜像站、运行集群，或规则正在使用的通知渠道解绑/缩权）：在删除、解绑、缩减 `projectIds` 或收窄 `scope` 时校验下游引用，仍在使用时返回 `409 Conflict`。
   - **弱筛选/集合类引用或父级清理**（如项目空间/应用/部署配置删除后在通知规则 `filter_json`、出站例外 `DeploymentTargetIDs`、`ScopedResourceProjectBinding` 中的残留引用，以及渠道/模板删除后的规则引用）：在同一事务内同步清理下游残留 ID。
2. **前端表单防御性过滤**：编辑弹窗初始化或构建提交载荷时，对照当前可用资源列表过滤掉已不存在的旧 ID（或在 UI 上显式标出失效项供用户移除）。
3. **“空集合代表全量匹配/放行”时必须 Fail-Closed 防静默扩权**：对于 `applicationIds: []`（匹配全部应用）或出站例外 `deployment_target_ids = ''`（放行整个项目）这类语义，剥离已删除 ID 后若从非空退化为空，后端必须自动停用规则或删除该条收窄授权，前端必须在表单上显式提示并阻断保存，要求用户主动清空或重新选择存活目标，绝不能静默放大通知或网络权限范围。
