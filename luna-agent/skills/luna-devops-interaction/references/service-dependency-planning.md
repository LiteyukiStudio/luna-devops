## 先建立交付拓扑

在创建任何应用或安装依赖前，先从仓库、模板、镜像、配置样例和用户目标中建立服务图。
至少识别：

- 可独立运行的前端、API、Worker、Agent、定时任务和后台消费者。
- 数据库、缓存、消息队列、对象存储、搜索、向量库、身份服务和可观测组件。
- 构建、启动、迁移、初始化、健康检查、端口、持久化和服务间调用关系。
- 哪些组件已存在于目标项目空间、同集群或用户可访问的外部平台。

把每个节点标记为 `业务服务`、`有状态依赖`、`共享平台能力`、`一次性任务` 或
`外部托管服务`。没有完成拓扑识别时，不要因为仓库根目录只有一个 README、Compose 或
Helm Chart 就创建一个包含所有容器的应用。

## 决定应用边界

出现任一条件时，把运行组件拆成独立应用或独立部署配置：

- 使用不同 Dockerfile、镜像、构建上下文或启动命令。
- 具有独立发布版本、扩缩容、重启、回滚、资源规格或故障恢复需求。
- 暴露不同端口、拥有不同健康检查，或需要不同网络、Secret 和存储边界。
- 生命周期不同，例如前端、API、Worker、Agent、数据库和队列不能同时销毁。

同一进程镜像中必须共同启动、共同发布、共同扩缩容的紧密组件可以保留为一个应用。
initContainer、迁移 Job、部署 Hook 和一次性初始化默认归属对应应用或发布流程，不要仅因
存在独立命令就创建长期运行的空应用。

## 决定依赖归属

对每个依赖依次判断以下事实，不能只按名称相同决定复用：

1. **所有权与安全边界**：是否属于同一用户、项目空间、环境和可信团队；是否存在可靠的
   Database、Schema、ACL、vhost、Bucket、Index、Collection 或 Namespace 隔离能力。
2. **生命周期**：依赖是否应随当前解决方案创建、保留和删除；复用后删除当前应用是否会
   影响其他业务。
3. **兼容性**：版本、扩展、模块、存储引擎、协议、持久化和备份策略是否满足来源事实。
4. **容量与故障域**：资源余量、连接数、吞吐、延迟、淘汰策略和可用性目标是否兼容；是否
   会产生不可接受的噪声邻居或级联故障。
5. **位置与连通性**：目标集群、命名空间、网络策略、TLS 和服务发现是否允许连接。
6. **运维与计费**：升级、备份、恢复、监控、配额和成本能否明确归属。

根据事实选择且只选择一种结果：

- `reuse_existing`：复用现有实例，并为当前解决方案创建独立的逻辑租户、凭据和服务引用。
- `solution_private`：为当前解决方案创建一个依赖，由其中多个业务服务共享。
- `service_dedicated`：为单个应用创建专用依赖。
- `external_managed`：绑定用户已经确认的外部托管服务，不在平台重复部署。
- `need_user_choice`：存在多个合理方案或复用影响成本、数据和故障域时，用交互卡片让用户选择。

没有读取到现有实例的实时状态、兼容性和作用域时，不得擅自选择 `reuse_existing`。不要让
用户手填资源 ID；先用平台工具发现可信候选。复用不等于复用 Secret，每个解决方案仍应
使用最小权限的独立凭据。

## 常见组件默认策略

以下是缺少用户特殊要求时的默认起点，不得覆盖来源文档中的硬性约束：

| 组件 | 默认决策 | 复用时必须满足 |
| --- | --- | --- |
| PostgreSQL、MySQL、MariaDB、MongoDB | 优先评估 `reuse_existing`；否则 `solution_private` | 独立 Database/Schema、用户和 Secret；版本/扩展、容量、备份及删除边界兼容 |
| Redis、Valkey、Memcached | 默认 `solution_private`，同一解决方案的 API、Worker、Agent 可共享；跨解决方案默认不复用 | 独立 ACL/凭据和 Key 前缀，内存、淘汰、持久化与管理命令策略兼容；Redis logical DB 不能作为强安全隔离 |
| RabbitMQ | 优先评估共享 Broker | 独立 vhost、用户、权限、配额和死信策略；插件与版本兼容 |
| Kafka、Redpanda | 优先评估共享集群 | 独立 Topic、ACL、Consumer Group、配额和保留策略；吞吐与分区容量充足 |
| NATS、JetStream | 优先评估共享集群 | 独立 Account/User、Subject 权限、Stream 和存储配额 |
| S3、MinIO、Garage、对象存储 | 优先评估共享实例或 `external_managed` | 独立 Bucket/Prefix、凭据、配额、生命周期和公开访问策略 |
| Elasticsearch、OpenSearch | 谨慎复用现有集群 | 独立 Index/Alias/API Key，插件、Mapping、分片、容量和保留策略兼容 |
| Meilisearch、Typesense | 默认 `solution_private`；低风险轻量业务可选择共享 | 独立 Index/API Key，版本、容量和删除边界兼容 |
| Qdrant、Weaviate、Milvus、向量数据库 | 根据数据隔离与容量选择共享或专用 | 独立 Collection/Tenant、凭据、Embedding 维度、索引参数和备份策略兼容 |
| Prometheus、Grafana、Loki、Tempo、OTel Collector | 默认复用平台可观测能力，不为普通应用重复部署 | Tenant、数据源、标签、保留期和访问权限满足需求；用户明确要求独立栈时再创建 |
| Gateway、Ingress、证书管理器、DNS Provider | 默认复用平台能力，只为应用创建 Route/Certificate 等业务资源 | 目标域名、命名空间、GatewayClass、证书签发和权限范围兼容 |
| Vault、Secret Manager、OIDC、SMTP 等平台集成 | 优先绑定已配置的受控 Provider | 独立策略、角色或凭据；不得把共享密钥复制进会话或普通环境变量 |
| PVC、文件卷 | 默认 `service_dedicated` | 只有用户明确要求接入已有数据且访问模式、所有权、备份和删除策略匹配时才复用 |

共享组件的粒度是“解决方案”而不是单个容器。例如博客的 API、Worker 和 Agent 可以共享
一个博客专用 Redis；不要为三个服务创建三个 Redis，也不要默认接入另一个无关业务的
Redis。关系型数据库可以复用服务器实例，但应为博客创建独立数据库、账号和 Secret。

## 生成执行计划

在写操作前形成可核对的计划，至少包含：

- 需要新建、复用或绑定的应用与依赖。
- 每个业务服务的来源、构建边界、端口、部署顺序和依赖边。
- 每个依赖的决策结果、依据、隔离单元、凭据方式和删除语义。
- 数据迁移、一次性初始化、公开入口，以及哪些步骤需要批准或 MFA。

只有一个安全且有事实支持的方案时可以直接采用平台默认值；存在成本、数据保留、共享故障
域或安全权衡时，使用 `change_review` 或 `resource_configuration` 让用户确认。不要一次询问
所有 Kubernetes 高级字段，也不要把显然可以自动发现的资源重新交给用户选择。

示例：前后端分离博客通常规划为独立前端、API 和 Agent 应用；复用兼容的 PostgreSQL
服务器并创建独立数据库；创建一个博客解决方案私有的 Redis；数据库迁移归属 API 发布；
只为前端和需要公开访问的 API 创建网关入口。

## 执行与验收

1. 先创建或绑定依赖，回读隔离单元、凭据引用、实时健康和服务地址。
2. 创建业务应用及部署配置，通过平台服务引用或 Secret 引用连接依赖。
3. 按依赖图执行迁移、后端、Worker/Agent 和前端；互不依赖的构建可以并行。
4. 验证每条依赖边的 Service、Endpoint、网络策略、认证和应用侧连接状态。
5. 验证共享依赖没有覆盖其他租户的配置、凭据、数据、保留策略或删除责任。
6. 最终回读应用、Release、工作负载、依赖健康和用户要求的访问入口。

删除或重建解决方案时，只清理该解决方案拥有的资源。对 `reuse_existing` 和
`external_managed` 依赖，只删除当前解决方案的逻辑租户、凭据和引用；绝不能删除共享实例。
依赖仍在创建、迁移、恢复或不可达时，只能报告进行中或阻塞，不能把业务应用启动当作整体
交付完成。
