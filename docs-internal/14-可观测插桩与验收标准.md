# Luna DevOps 可观测插桩与验收标准

本文定义 API、Worker、Agent 和 Web 的统一 OpenTelemetry 约束。目标不是“接入了 SDK”，而是让一次用户操作从浏览器进入 API、经过数据库和外部平台、进入异步任务或 Agent 循环，直到最终状态都能被同一条链路解释。

Grafana、Tempo、Loki、Prometheus 和 Collector 的实际接入故障、查询陷阱与验收清单见 `docs-internal/16-Grafana可观测接入复盘.md`。

## 1. 覆盖目标

必须覆盖以下业务边界：

- 每个 HTTP、SSE、WebSocket 和内部服务请求。
- 每次 PostgreSQL、Redis 和 Asynq 访问。
- 每次 Kubernetes、Git Provider、Registry、OIDC、通知、Webhook、DNS、模型 Provider、网络搜索和网页读取调用。
- 每个异步任务的投递、排队、领取、重试、执行和终态。
- 每个 Agent Run 的循环、模型轮次、工具调用、审批、交互卡片和持久化。
- 构建、发布、部署、回滚、网关、证书、计费、通知等关键业务阶段。

“覆盖”要求一个边界至少具备 Span；关键状态转换同时具备结构化日志；可聚合的业务结果同时具备 Metric。不能只在接口入口创建一个 Span，然后把接口内部数据库、外部调用和业务阶段视为黑盒。

## 2. 最小运行配置

```env
OTEL_EXPORTER_OTLP_ENDPOINT=http://otel-collector:4318
```

只有该值非空时才启用 OTLP 导出；为空时使用无操作 Provider，不启动后台导出器，也不要求部署 Collector。以下配置均为可选：

```env
OTEL_RESOURCE_ATTRIBUTES=deployment.environment.name=production
OTEL_EXPORTER_OTLP_HEADERS=api-key=replace-me
```

统一使用 OTLP HTTP/protobuf。服务名由进程固定，不让部署者重复配置：

- `luna-devops-api`
- `luna-worker`
- `luna-agent`
- `luna-web`

## 3. Trace 标准

### 3.1 命名与层级

- Span 名称必须稳定，不包含用户 ID、项目 ID、资源名称、URL 查询参数等高基数值。
- HTTP Server Span 使用路由模板，例如 `GET /api/v1/projects/:projectId`。
- 数据库 Span 使用数据库系统、操作和表名语义属性；禁止记录 SQL 参数。需要记录 SQL 时只能使用脱敏、参数化 statement。
- 外部调用按协议和目标系统创建 Client Span，例如 `registry.manifest.get`、`kubernetes.deployment.apply`。
- 业务阶段使用 Internal 或 Producer/Consumer Span，例如 `release.prepare`、`build.enqueue`、`agent.tool.execute`。
- 资源 ID 放在 Span attribute；禁止放进 Span name 或 Metric label。

### 3.2 传播

- HTTP 使用 W3C `traceparent`、`tracestate` 和 Baggage。
- 浏览器 EventSource/WebSocket 无法设置自定义 Header 时，前端使用私有 `_otel_traceparent` / `_otel_tracestate` 参数传递；API 必须在 Trace 中间件前转入 Header 并立即从 URL 删除，业务 Handler 和日志不得看到这些参数。
- Asynq payload 只传播序列化后的 Trace Context，不复制用户 Cookie、Token 或请求正文。
- Worker 消费 Span 继承 Producer 上下文；跨时较长的批处理可使用 Span Link，并保留原 trace ID。
- API 到 Agent、Agent 回调 API、SSE/WebSocket 建连都必须延续上下文。
- Agent Run 通过数据库排队时，把经过白名单和长度限制处理的 `traceparent` / `tracestate` 与 Run 一起持久化；领取 Run 后必须以该上下文作为父 Context。遥测上下文不得参与业务幂等哈希，不持久化 Baggage，也不得通过 Timeline 或事件响应回显。
- Request ID 是日志检索和用户报错编号，不替代 Trace ID；两者都要保留。

### 3.3 结果与异常

- 成功 Span 保持 `Unset` 或 `Ok`；业务拒绝、依赖失败和终态失败设置 `Error`。
- 记录稳定 `error.code`、错误类型和可安全公开的依赖状态。默认不得记录 Secret、Token、Cookie、完整请求体、模型 Prompt、工具参数或第三方凭据。Agent 仅允许在 `AI_OBSERVABILITY_CAPTURE_CONTENT=true` 时记录经过统一强制脱敏和 32 KiB 单字段限制的模型与工具内容；Secret、Token、Cookie、密码、API Key 和 URL 凭据在该模式下仍禁止记录。
- 同一错误只在拥有终态语义的边界输出一次 Error 日志；下层只包装并在 Span 上记录异常，避免重复刷屏。

## 4. 结构化日志标准

Go 统一使用 `slog` JSON，Agent 使用 Pino JSON；两者都通过 OTel 日志桥接导出，并保留 stdout，避免 Collector 故障时完全失去日志。

每条关键日志至少包含：

| 字段 | 含义 |
| --- | --- |
| `event.name` | 稳定事件名，例如 `release.started` |
| `service.name` | 固定服务名 |
| `trace_id` / `span_id` | 当前链路关联字段 |
| `request_id` | 用户可见请求编号（存在时） |
| `operation` | 稳定业务操作 |
| `outcome` | `succeeded`、`failed`、`cancelled`、`rejected` |
| `error.code` / `error.type` | 失败时的稳定错误分类 |
| `resource.type` / `resource.id` | 相关资源；仅日志和 Span 使用 |

级别约束：

- `INFO`：启动完成、业务操作开始/完成、状态转换、任务领取/完成、审批结果。
- `WARN`：将重试、可恢复依赖故障、降级、输入被拒绝、限流。
- `ERROR`：操作进入失败终态、不可恢复依赖错误、进程无法启动。
- `DEBUG`：开发排障细节；不得用来弥补缺失的关键 INFO 日志。

## 5. Metric 标准

Metric 只使用有限集合的低基数标签。用户 ID、项目 ID、应用 ID、请求 ID、Trace ID、URL、错误正文和外部资源名禁止成为标签。

全服务至少提供：

- RED：请求/操作次数、错误数、耗时、进行中数量。
- 依赖：PostgreSQL/Redis 连接池，外部平台调用次数、错误、耗时。
- Worker：队列深度、等待时间、执行时间、重试、丢弃和各终态。
- Agent：Run 数量/耗时/终态、循环轮次、Provider 请求、首 Token 延迟、Token 用量、工具调用、审批等待和中断。
- 交付：构建、发布、部署、回滚、网关和证书的结果与阶段耗时。
- 平台：通知/Webhook 投递、计费计量、实时观察不可用、认证拒绝和限流。

通用业务指标：

```text
luna_devops_operation_total{service,domain,operation,outcome}
luna_devops_operation_duration_seconds{service,domain,operation}
```

现有 Prometheus `/metrics` 可以继续作为兼容抓取入口，但所有新通用指标必须同时通过 OTel Meter 生成，避免维护两套业务统计口径。

## 6. 模块插桩规则

### API

- Gin 中间件自动覆盖所有已注册路由，并以路由模板命名。
- GORM、`database/sql`、go-redis 和默认 HTTP Client 在构造处统一插桩，不允许 Handler 临时包一层假装覆盖。
- Handler 只补业务阶段 Span；Repository/Provider 负责数据库和外部依赖边界。
- SSE/WebSocket 记录建连、断开和终态，不为每条心跳创建 Span。

### Worker

- Producer 在任务头中注入 Trace Context，Consumer 提取后建立消费 Span。
- 每次尝试单独记录执行 Span；重试与原业务链路关联。
- Kubernetes 等外部调用由 Provider Client Transport 自动插桩；构建/部署阶段另建业务 Span。

### Agent

- 一个 Run 是根业务边界，每轮模型调用、每个工具调用和持久化操作都是子 Span。
- Run 已带上游上下文时是原用户请求的异步子边界；没有上游上下文时才作为新的根业务边界。
- Node 自动插桩必须按实际边界显式引入。当前只启用 HTTP、Fastify、PostgreSQL、Pino 和 Undici；不得使用会捆绑未使用云探测器、数据库驱动或消息客户端的全量元包。
- Fastify 使用维护方提供的 `@fastify/otel`，并与 HTTP instrumentation 共同完成入口提取、路由命名和上游父链关联；数据库、日志和出站请求分别由单一 instrumentation 负责，避免重复 Span。
- 流式响应记录首 Token 延迟和完成/中断，不为每个 Token 建 Span 或日志。
- 工具名、Provider 类型和模型类型可用于低基数标签。用户 Prompt、工具参数和模型原始输出默认不得写入遥测；显式启用高敏内容观测时只能通过统一 `recordAIContent` 入口写入 Span Event 和关联日志，不得直接设置普通 Span attribute 或散落日志。

### Web

- 页面导航、用户操作和 API 请求建立浏览器 Span，并向 API 注入 W3C Trace Context。
- 只上报路由模板、操作类型、耗时和稳定错误码，不上报表单内容、DOM 文本、URL 查询值或本地存储内容。
- 浏览器遥测失败不得阻塞主流程。

## 7. 覆盖门禁

自动插桩提供基础覆盖，人工清单防止新业务绕过统一入口：

1. 所有 Gin 路由必须经过 Trace 中间件。
2. 所有 GORM/Redis/HTTP/Kubernetes 客户端必须由统一构造器返回。
3. 所有 Asynq Handler 必须经过 Trace/Metric/Log 中间件。
4. 所有 Agent Tool 和 Provider 必须经过统一执行包装器。
5. 禁止新增 `log.Printf`、裸 `http.Client{}`、未插桩数据库连接和输出 Secret 的日志。
6. 新增 Node instrumentation 前必须检查其完整生产依赖树；能够由少量单项包覆盖时，不得为便利引入包含无关 Provider、云探测器或运行时适配器的元包。

CI/测试至少断言：父子 Trace Context 能传播、错误状态正确、Metric 标签集合稳定、日志包含关联字段；默认模式不出现模型和工具正文，高敏内容模式能出现脱敏与截断后的正文，任何模式都不得出现凭据。

## 8. 验收标准

使用一个临时本地 OTel Collector/可视化栈完成以下旅程，临时部署文件不进入仓库：

1. API 健康检查和一个带数据库查询的列表请求。
2. 一个 Redis/Asynq 任务从投递到 Worker 消费完成。
3. 一个失败的外部依赖调用，确认 Trace 显示错误边界且日志给出稳定错误码。
4. 一个 Agent 多轮 Run，至少包含模型调用、工具调用和持久化。
5. 一个从 Web 发起并延续到 API 的请求。

验收通过条件：

- 查询任一请求都能看到入口、数据库/Redis/外部调用和业务阶段的父子层级。
- 错误 Trace、相关日志和 Metric exemplar/时间窗口能相互关联。
- Collector 不可达时业务仍可运行，stdout 日志仍存在，后台导出器不会无限阻塞退出。
- 遥测数据中抽查不到 Token、Secret、Cookie、密码、模型 Prompt 或请求正文。
