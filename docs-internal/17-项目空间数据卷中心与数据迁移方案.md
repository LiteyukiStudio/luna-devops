# 项目空间数据卷中心与数据迁移方案

## 1. 状态与目标

本文是未完成的跨模块实施方案，目标是将当前“部署配置中的 PVC + 应用删除后的
`RetainedVolume`”重构为项目空间级数据卷中心，一次性确定以下完整边界：

- 数据卷从创建起就是独立于应用和部署配置的项目空间资产。
- 项目空间统一查看未消费、已预留、使用中和异常数据卷，实时状态来自 Kubernetes。
- 空白卷创建、已有 PVC 引用/纳管、CSI VolumeSnapshot 恢复和外部数据归档导入使用
  同一个领域模型。
- 上传和下载为可续传、可重试、有进度和校验和的异步 Transfer，不再绑定原始 HTTP
  请求生命周期。
- 部署、Worker、Kubernetes Provider、计费、Agent Tool、CLI 和 Web 使用同一套权限、
  状态和错误码。

本方案完成后，旧 `retained_volumes` 表、`DeploymentTarget.DataVolumes` JSON 字符串、
`DataRetentionEnabled` 开关和按部署目标计费的存储模型应被删除；不保留长期双读、
宽松 JSON 解析或“未传新字段则走旧逻辑”的运行时兼容分支。

## 2. 核心设计决策

1. **PVC 生命周期与部署解耦。** PVC 始终带有 `luna.devops/project-volume-id` 和项目空间
   归属标签，不再在删除应用时从“应用 PVC”改标签为“保留 PVC”。
2. **期望状态与实时观察分离。** PostgreSQL 保存资产归属、期望规格、挂载关系和任务
   历史；PVC phase、实际容量、存在性和当前挂载情况每次从 Kubernetes 读取。
3. **消费状态由挂载关系派生。** `available/reserved/in_use` 不作为可与关系表分裂的
   独立事实存储；由数据卷生命周期和活动挂载记录统一派生。
4. **传输数据不进业务库。** 归档使用后端 `VolumeTransferStore` 适配的 S3-compatible 私有
   对象存储暂存；PostgreSQL 只保存对象引用、大小、SHA-256、进度和过期时间。
5. **Web/CLI 不直接编排 S3 API。** 上传采用 Luna API 提供的可续传分块协议，下载由
   Luna API 代理对象存储并支持 HTTP Range。
6. **大数据操作只在 Worker 执行。** API 只建立资产/传输记录、校验权限并投递 Asynq；
   PVC 创建、Snapshot、安全解包、归档、删除和清理均在 Worker/Transfer Job 内完成。
7. **文件系统卷和块卷显式分流。** Filesystem 卷使用 `tar.gz`；Block 卷使用 `raw.zst`，
   部署时使用 `volumeDevices/devicePath`，不再把 Block 卷错当文件目录挂载。
8. **同一数据卷只有一个权威服务。** Handler 不直接改数据卷状态；统一通过
   `internal/volume.Service` 完成权限后的不变式、并发、幂等、Repository 和 Provider 编排。

## 3. 领域概念与不变式

### 3.1 ProjectVolume

`ProjectVolume` 是项目空间可挂载的持久数据资产，对应一个确定集群和 Namespace 中的
PVC。PVC 名称为稳定技术标识 `luna-pvol-<short-id>`，修改展示名不改 PVC 名称。

来源 `sourceKind` 固定为：

- `blank`：从空白 PVC 创建。
- `managed`：从旧部署目标托管 PVC 迁移而来。
- `retained`：从旧 `RetainedVolume` 迁移而来。
- `archive_import`：从外部 `tar.gz` 或 `raw.zst` 导入。
- `snapshot_restore`：从同集群可用 CSI VolumeSnapshot 恢复。
- `existing_claim`：引用或显式纳管已有 PVC。

底层数据所有权 `ownershipMode` 固定为：

- `managed`：平台负责创建、计费、挂载、保留和最终删除 PVC。
- `referenced`：平台只记录和挂载，从不删除底层 PVC，不对申明容量计费。

生命周期 `lifecycleState` 只表示平台工作流：

- `provisioning`：正在创建 PVC 或等待导入。
- `ready`：数据卷资产可被绑定；PVC 可因 `WaitForFirstConsumer` 仍处于 Pending。
- `deleting`：删除任务已投递。
- `error`：最近一次创建、导入或删除进入失败终态，可显式重试。

消费状态 `availability` 从挂载记录派生：

- `available`：`ready` 且没有活动挂载。
- `reserved`：已被部署配置引用，但尚未有成功 Release 将关系激活。
- `in_use`：至少一条挂载关系已由 Worker 从 Kubernetes 权威回读确认。
- `unavailable`：生命周期不是 `ready`，或观察不可用。

### 3.2 DeploymentVolumeMount

`DeploymentVolumeMount` 代替 `DeploymentTarget.DataVolumes` JSON，表示部署配置的持久卷或
`emptyDir` 挂载意图。

不变式：

- 同一部署配置内 `logicalName`、`mountPath/devicePath` 唯一且不得嵌套。
- `ReadWriteOnce/ReadWriteOncePod` 一律按平台级单写者处理，最多一条活动挂载。
- `ReadOnlyMany` 只允许 `readOnly=true`的多挂载。
- `ReadWriteMany` 可多挂载，但每条关系仍必须经后端权限和集群兼容校验。
- Filesystem 卷使用 `mountPath`；Block 卷必须使用 `devicePath`，两者不能同时提供。
- 数据卷、部署配置、项目空间和集群必须一致；不支持跨集群直接挂载。

### 3.3 VolumeTransfer

`VolumeTransfer` 是导入或导出工作流，方向 `direction` 为 `import/export`，状态为：

```text
created -> uploading -> queued -> running -> succeeded
   |           |          |          |
   +-----------+----------+----------+-> failed
               +-----------------------> cancelled
created/uploading ----------------------> expired
```

- `uploading` 只用于外部归档导入。
- `succeeded/failed/cancelled/expired` 为终态，不在同一记录上回退；重试新建 Transfer。
- 一个数据卷同时最多一个修改内容的 Import；Export 可与挂载并存，但一个卷同时
  最多一个运行中 Export。
- 进度、校验和和归档引用是工作流历史；归档本体不进入 PostgreSQL。

## 4. 数据库设计

### 4.1 `project_volumes`

| 字段 | 类型 / 约束 | 含义 |
| --- | --- | --- |

| `cluster_id` | text, not null, index | 所在运行集群 |

| `claim_name` | text, not null | 稳定 PVC 名称 |
| `ownership_mode` | enum check | `managed/referenced` |
| `source_kind` | enum check | 见 3.1 |
| `lifecycle_state` | enum check, index | `provisioning/ready/deleting/error` |

| `capacity_bytes` | bigint, not null | 规范化容量，用于配额、计费和稳定排序 |
| `storage_class_name` | text, not null | 期望 StorageClass |
| `access_mode` | enum check | `ReadWriteOnce/ReadWriteOncePod/ReadOnlyMany/ReadWriteMany` |
| `volume_mode` | enum check | `Filesystem/Block` |
| `source_application_id` | nullable text | 迁移追溯，不参与归属判断 |
| `source_application_name` | text, not null | 来源展示快照，源应用删除后仍可识别 |
| `source_deployment_target_id` | nullable text | 迁移追溯 |
| `created_by` | text, not null | 创建/导入/纳管人 |
| `revision` | bigint, not null | 乐观并发版本 |
| `last_error_code` | text, not null | 稳定错误码 |
| `last_error_message` | text, not null | 内部诊断，生产 API 不直出 |
| `created_at/updated_at/deleted_at` | timestamptz | 审计时间 |

索引与约束：

- 唯一 `(cluster_id, namespace, claim_name) WHERE deleted_at IS NULL`。
- 唯一 `(project_id, lower(display_name)) WHERE deleted_at IS NULL`。
- 列表索引 `(project_id, lifecycle_state, created_at DESC)`。
- `referenced` 数据卷的 `source_kind` 必须为 `existing_claim`。

### 4.2 `deployment_volume_mounts`

| 字段 | 类型 / 约束 | 含义 |
| --- | --- | --- |
| `id` | text PK, `dvmt_` | 挂载关系 ID |
| `project_id/application_id/deployment_target_id` | text, not null, indexes | 业务归属 |
| `source_type` | enum check | `project_volume/empty_dir` |
| `project_volume_id` | nullable FK | 持久卷引用 |
| `logical_name` | text, not null | 容器 volume name |
| `mount_path` | nullable text | Filesystem 挂载路径 |
| `device_path` | nullable text | Block 设备路径 |
| `read_only` | boolean, not null | 容器挂载属性 |
| `exclusive` | boolean, not null | 用于单写者部分唯一索引 |
| `activation_state` | enum check | `reserved/active/release_pending/error` |
| `empty_dir_medium/size_limit` | text | 仅 `empty_dir` 使用 |
| `last_error_code/message` | text | 挂载/解绑工作流结果 |
| `created_at/updated_at/deleted_at` | timestamptz | 时间 |

索引与约束：

- 唯一 `(deployment_target_id, logical_name) WHERE deleted_at IS NULL`。
- 唯一 `(deployment_target_id, mount_path) WHERE deleted_at IS NULL AND mount_path IS NOT NULL`。
- 唯一 `(deployment_target_id, device_path) WHERE deleted_at IS NULL AND device_path IS NOT NULL`。
- 唯一 `(project_volume_id) WHERE deleted_at IS NULL AND exclusive = true AND activation_state IN ('reserved','active')`。
- `source_type=project_volume` 时 `project_volume_id` 必填；`empty_dir` 时必须为空。

### 4.3 `volume_transfers`

| 字段 | 类型 / 约束 | 含义 |
| --- | --- | --- |
| `id` | text PK, `vtx_` | Transfer ID |
| `project_id/project_volume_id` | text, not null, indexes | 归属 |
| `direction` | enum | `import/export` |
| `format` | enum | `tar_gz/raw_zst` |
| `consistency_mode` | enum | `snapshot/live/unmounted` |
| `state` | enum, index | 见 3.3 |
| `object_key` | text, not null | 私有 bucket 内部引用，不回显 |
| `multipart_upload_id` | text | 对象存储分块上传状态 |
| `source_filename` | text | 脱敏后的展示名，不进入遥测 |
| `expected_bytes/transferred_bytes` | bigint | 大小和进度 |
| `sha256` | text | 完成后必填 |
| `actor_id` | text, not null | 发起人 |
| `expires_at/started_at/finished_at` | timestamptz | 会话、工作和临时对象周期 |
| `last_error_code/message` | text | 稳定错误码和内部诊断 |
| `created_at/updated_at` | timestamptz | 时间 |

另建 `volume_transfer_parts(transfer_id, part_number, offset, size, etag, sha256, state,
lease_token, lease_expires_at, created_at, updated_at)`，唯一 `(transfer_id, part_number)` 与
`(transfer_id, offset)`。`reserved` 行先在短事务内固定 partNumber/checksum/租约，S3 `WritePart`
在事务外执行，再用 lease token 短事务 CAS 为 `completed`；只有 completed 行推进 offset。
租约过期后仅允许相同 size/checksum 接管并重写同一 partNumber，异内容稳定冲突。这样 API 多副本
可以恢复进程崩溃，同时不会在慢对象存储请求期间占用 PostgreSQL 连接或行锁。

## 5. Kubernetes 资源映射

### 5.1 PVC

平台纳管 PVC 固定标签：

```yaml
app.kubernetes.io/managed-by: luna-devops
luna.devops/project-id: <project-id>
luna.devops/project-volume-id: <project-volume-id>
```

PVC 不再使用 application/deployment-target 标签表达生命周期所有权。工作负载通过
`deployment_volume_mounts` 引用稳定 `claim_name`，因此删除应用或部署配置只解绑，不需要
修改 PVC 标签才能保留数据。

### 5.2 实时观察

`internal/volume.ObservationService` 按列表当前页次将数据卷按 `(cluster, namespace)` 分组，每组
一次 List/Get PVC，不得对每行建立独立 Client 或无界全量查询。响应添加：

```json
{
  "observation": {
    "status": "available",
    "exists": true,
    "phase": "Bound",
    "capacity": "20Gi",
    "storageClassName": "standard",
    "accessModes": ["ReadWriteOnce"],
    "volumeMode": "Filesystem",
    "boundVolumeName": "pvc-...",
    "observedAt": "2026-08-15T12:00:00Z",
    "observationCode": ""
  }
}
```

列表和详情均设置 `Cache-Control: no-store`。集群不可达时保留数据库中的期望配置，
`observation.status=unavailable`，并返回稳定 `observationCode`，不使用上次成功状态。

### 5.3 Transfer Job

新增 `cmd/volume-transfer`，与 Worker 使用同一镜像交付，镜像内同时包含
`luna-worker` 和 `luna-volume-transfer`。Worker 为每次 Transfer 创建独立 Kubernetes Job：

- Job 挂载目标 PVC，Import 可写，Export 只读。
- Job 的 `/tmp` scratch 与 ephemeral-storage 按服务端动态分块加安全余量设置；5 TiB 上限对应
  525 MiB 分块，禁止使用固定 128 MiB 临时盘造成大卷任务 ENOSPC。
- Job 使用限时、限 Transfer 的随机回报 Token；数据库只保存 Token hash。
- Token 通过临时 Kubernetes Secret 以文件方式挂载，不出现在命令行、日志或 Pod annotation。
- Job 只访问 Luna API 内部 Transfer 端点，不获取对象存储长期凭据。
- Worker 使用平台配置的 `VOLUME_TRANSFER_CALLBACK_BASE_URL` 生成 Job 回调地址；该地址必须是
  运行集群可达的 HTTPS Luna API 入口，不使用请求 Host 或用户输入拼接。
- Transfer Job 镜像由 `VOLUME_TRANSFER_JOB_IMAGE` 显式配置并固定到与 Worker 相同版本；任务
  投递前检查集群能否拉取镜像、访问回调入口和对应对象存储适配路径。
- 受限出站策略只允许 Transfer Job 访问经管理员配置的 Luna API 回调目标；不为项目空间
  普通工作负载放开相同出站权限。
- Asynq `traceparent/tracestate` 传到 Worker，Worker 把白名单 Trace Context 传给 Job，Job 回报继续
  原链路或使用 Span Link。
- Job、Secret、Snapshot 和临时 PVC 在终态后由独立 cleanup Context 限时清理，并由周期
  Reconciler 补偿遗留资源。

Filesystem 解包由 Go 实现，不直接调用 `tar -x`。必须拒绝绝对路径、`..` 穿越、
越界 symlink/hardlink、device node、setuid/setgid 和超限文件；解压后总字节不得超过 PVC
容量，默认最多 100 万个文件。Block 导入要求解压后原始长度不大于设备容量。

## 6. 公开 API 契约

所有路由放在 `/api/v1/projects/{projectId}` 下。高增长列表必须返回
`items/page/pageSize/sortBy/sortOrder/total/totalPages`，默认 `page=1&pageSize=20`，最大
`pageSize=100`。未知排序字段返回 `pagination.sort_by_invalid`，不回显用户输入到 SQL。

### 6.1 数据卷

| Method | Path | operationId | 用途 | 权限 |
| --- | --- | --- | --- | --- |
| GET | `/volumes` | `listProjectVolumes` | 分页查询卷和当前页实时观察 | `volume:read` |
| GET | `/volume-storage-classes` | `listProjectVolumeStorageClasses` | 分页读取集群存储类和 Snapshot/扩容能力 | `volume:read` |
| POST | `/volumes` | `createProjectVolume` | 创建空白卷、引用/纳管 PVC 或从 Snapshot 恢复 | `volume:write` |
| GET | `/volumes/{volumeId}` | `getProjectVolume` | 详情、挂载和实时观察 | `volume:read` |
| PATCH | `/volumes/{volumeId}` | `updateProjectVolume` | 改展示名或扩容 | `volume:write` |
| POST | `/volumes/{volumeId}/retry` | `retryProjectVolumeOperation` | 重试最近失败的创建、恢复或删除 | 原操作对应权限 |
| POST | `/volumes/{volumeId}/deletion-preview` | `previewProjectVolumeDeletion` | 回读挂载、Transfer 和底层删除影响 | `volume:delete` |
| DELETE | `/volumes/{volumeId}` | `deleteProjectVolume` | 异步删除托管数据或移除外部引用 | `volume:delete` + 明确确认 |

`GET /volumes` 支持：

- `search`：展示名、PVC 名和来源应用名的后端受控搜索。
- `availability=available|reserved|in_use|unavailable`。
- `lifecycleState=provisioning|ready|deleting|error`。
- `clusterId`、`sourceKind`、`ownershipMode`、`volumeMode`。
- `sortBy=createdAt|updatedAt|displayName|capacity`，`sortOrder=asc|desc`。

列表 item 和详情共用的 `ProjectVolume` 响应核心结构为：

```json
{

  "projectId": "proj_...",
  "displayName": "postgres-data",
  "clusterId": "rclu_demo",
  "namespace": "project-demo",
  "claimName": "luna-pvol-abcd1234",
  "ownershipMode": "managed",
  "sourceKind": "archive_import",
  "lifecycleState": "ready",
  "availability": "available",
  "capacity": "20Gi",
  "capacityBytes": 21474836480,
  "storageClassName": "standard",
  "accessMode": "ReadWriteOnce",
  "volumeMode": "Filesystem",
  "bindingSummary": { "reserved": 0, "active": 0 },
  "revision": 3,
  "observation": {
    "status": "available",
    "exists": true,
    "phase": "Bound",
    "capacity": "20Gi",
    "observedAt": "2026-08-15T12:00:00Z",
    "observationCode": ""
  },
  "createdAt": "2026-08-15T11:00:00Z",
  "updatedAt": "2026-08-15T12:00:00Z"
}
```

详情在此基础上增加 `bindings[]` 和最近 Transfer 摘要；列表不内联无界历史。

`GET /volume-storage-classes` 必须传 `clusterId`，同样使用默认 20/最大 100 分页，每项
返回 `name/provisioner/isDefault/allowVolumeExpansion/volumeBindingMode/snapshotSupported`。它从
Kubernetes StorageClass/VolumeSnapshotClass 实时读取、`no-store`，前端创建/导入表单必须使用
该接口选择，不让普通用户手填 StorageClass。

创建请求使用判别联合：

```json
{
  "displayName": "postgres-data",
  "clusterId": "rclu_demo",
  "capacity": "20Gi",
  "storageClassName": "standard",
  "accessMode": "ReadWriteOnce",
  "volumeMode": "Filesystem",
  "source": { "type": "blank" }
}
```

```json
{
  "displayName": "legacy-data",
  "clusterId": "rclu_demo",
  "source": {
    "type": "existingClaim",
    "claimName": "legacy-pvc",
    "ownershipMode": "referenced"
  }
}
```

```json
{
  "displayName": "snapshot-restore",
  "clusterId": "rclu_demo",
  "capacity": "100Gi",
  "source": {
    "type": "volumeSnapshot",
    "snapshotName": "nightly-2026-08-15"
  }
}
```

`POST /volumes` 必须带 8–160 字符的 `Idempotency-Key`，返回 `202 Accepted` 和
`ProjectVolume{lifecycleState:"provisioning"}`。`existingClaim` 只允许项目空间对应 Namespace；
`ownershipMode=managed` 属于纳管，必须在修改标签前查询 Pod 引用和现有归属，存在其他
工作负载或冲突项目标签时 fail closed，不提供 `force=true` 旁路。

`PATCH` 必须带 `If-Match: <revision>`。容量只能增加；修改 StorageClass、accessMode 或
volumeMode 必须通过新卷 + Transfer 迁移，不伪装成就地更新。

`DELETE` 使用 `dataAction=delete|detach`：`managed` 只允许 `delete`，`referenced` 只允许
`detach`。存在 `reserved/active` 挂载或运行中 Transfer 时返回 `409 volume.in_use`，不级联
强制解绑。

```json
  "volume": { "id": "pvol_...", "lifecycleState": "provisioning" },
  "transfer": {
    "id": "vtx_...",
    "direction": "import",
    "state": "uploading",
    "uploadOffset": 0,
    "chunkSize": 67108864,
    "expiresAt": "2026-08-16T12:00:00Z"
  }
}
```

上传协议使用 Luna API 路径下的 TUS 1.0 Core + Checksum 子集：

- 每个 `PATCH` 必须带 `Tus-Resumable: 1.0.0`、`Upload-Offset`、`Content-Type:
  application/offset+octet-stream` 和 `Upload-Checksum: sha256 <base64>`。
- 服务端按 `max(64 MiB, ceil(contentLength / 10000))` 计算必需分块，并向上取整到 MiB；
  `VolumeTransfer.chunkSize` 与 HEAD/PATCH 的 `Upload-Chunk-Size` 是唯一事实源。5 TiB 使用
  525 MiB，只有最后一块可较小，所有客户端禁止自行选择更小分块；S3 单 part 上限保持 5 GiB。
- API 先在 0700 专用 spool 目录把有界请求体流式写入 0600 临时文件，边写边校验长度、
  `context` 与分块 SHA-256；校验完成后才进入 part reservation 短事务。随后事务外调用 S3
  `WritePart`，最后按 lease CAS 提交 ETag/offset，任何失败和取消都会删除临时文件。
- spool 使用进程级加权 byte budget，创建文件前检查磁盘余量；启动只清理匹配平台前缀且超过
  安全年龄的孤儿文件。预算繁忙、目录不可用、磁盘不足分别返回稳定 429/503/507，禁止回退到
  OS 默认临时目录的无界使用或在内存中缓存大分块。
- offset 不匹配返回 `409 volume_transfer.offset_mismatch` 并在 `Upload-Offset` 返回服务端值。
- 分块校验和不匹配返回 `460 volume_transfer.chunk_checksum_mismatch`，该 offset 不前进。
- `complete` 校验已提交分片、总长度和声明的完整 SHA-256 格式；通过后返回 `202`，
  Transfer 进入 `queued`。API 不在请求内同步回读大对象；Import Transfer Job 流式读取归档时
  计算完整 SHA-256，并在写入业务成功前通过内部回调与声明值比对。
- 上传会话默认 24 小时过期；默认单卷上传上限 100 GiB，部署管理员可通过
  `VOLUME_TRANSFER_MAX_BYTES` 在 1 GiB–5 TiB 范围调整。

### 6.3 导出、Transfer 查询和下载

| Method | Path | operationId | 用途 | 权限 |
| --- | --- | --- | --- | --- |
| POST | `/volumes/{volumeId}/exports` | `createVolumeExport` | 建立异步 Export | `volume:export` |
| GET | `/volume-transfers` | `listVolumeTransfers` | 分页查询 Transfer | `volume:read` |
| GET | `/volume-transfers/{transferId}` | `getVolumeTransfer` | 进度和终态 | `volume:read` |
| POST | `/volume-transfers/{transferId}/retry` | `retryVolumeTransfer` | 从未过期归档创建新 Transfer | 原 Transfer 对应权限 |
| POST | `/volume-transfers/{transferId}/cancel` | `cancelVolumeTransfer` | 取消非终态 Transfer | 创建者或 `volume:delete` |
| POST | `/volume-transfers/{transferId}/download-authorizations` | `authorizeVolumeTransferDownload` | 签发一次性下载票据 | `volume:export` + 有效 Session/OAuth Grant |
| HEAD | `/volume-transfers/{transferId}/content` | `headVolumeTransferContent` | 大小、ETag、Range 能力 | 下载票据 |
| GET | `/volume-transfers/{transferId}/content` | `downloadVolumeTransferContent` | 支持 Range 的归档下载 | 下载票据 |

导出请求：

```json
{
  "format": "tar_gz",
  "consistency": "auto"
}
```

`consistency` 语义：

- `auto`：未挂载卷直接只读导出；使用中卷在集群支持 CSI Snapshot 时从 Snapshot
  创建临时 PVC 导出，不支持时返回 `volume.snapshot_required`。
- `snapshot`：必须通过 CSI Snapshot；Snapshot 只保证 crash-consistent，不宣称 application-consistent。
- `live`：显式接受在线 Filesystem 可能不一致；只允许 Owner/Admin，请求与审计必须记录
  该选择。Block 卷稳定拒绝 `live`，只能使用 `snapshot` 或在未挂载时使用 `unmounted`。

`GET /volume-transfers` 支持 `direction/state/volumeId/createdBy/sortBy/sortOrder`，默认按
`createdAt desc`。Viewer/Developer 只能看到 Transfer 状态和稳定错误码；`sourceFilename` 仅创建者和
Owner/Admin 可见。`retry` 始终创建新 Transfer ID：Import 只在已完成上传的对象尚未过期时免重传，
新的 Transfer Job 仍会流式复核完整 SHA-256；
Export 重新执行快照/归档，不复用可能过时的导出内容。

导出成功后归档默认保留 24 小时。下载票据 60 秒内必须首次使用，绑定 user、
session/OAuth grant、project 和 transfer。首次使用后换取一个最长 30 分钟、只允许同
Transfer 和同用户的 Range 会话 Cookie，以便浏览器/CLI 断点续传；不在 URL 长期保留票据。

### 6.4 内部 Transfer Job API

路由放在 `/internal/v1/volume-transfers/{transferId}`，只接受 Worker 签发的限 Transfer Token：

| Method | Path | 用途 |
| --- | --- | --- |
| HEAD | `/content` | 取得内部续传 offset/大小 |
| PATCH | `/content` | Export Job 分块上传归档 |
| GET | `/content` | Import Job 按 Range 读取归档 |
| POST | `/progress` | 回报处理字节、文件数和当前阶段 |
| POST | `/complete` | 幂等提交终态和 SHA-256 |
| POST | `/fail` | 回报稳定错误码，原始 stderr 只进内部诊断 |

该 Token 不是用户 Token，不携带 Cookie、上传内容或对象存储凭据，不能访问其他平台
API。所有内部回报使用 Transfer ID + Token hash + 当前状态 CAS 校验。

## 7. 部署契约改造

`DeploymentTargetInput.dataVolumes` 从 JSON 字符串改为强类型数组：

```json
{
  "dataVolumes": [
    {
      "logicalName": "data",
      "sourceType": "projectVolume",
      "projectVolumeId": "pvol_...",
      "mountPath": "/var/lib/postgresql/data",
      "readOnly": false
    },
    {
      "logicalName": "cache",
      "sourceType": "emptyDir",
      "mountPath": "/cache",
      "emptyDir": { "medium": "", "sizeLimit": "2Gi" }
    }
  ]
}
```

- 普通 UI 不再允许手填 `existingClaimName`；必须先在数据卷中心引用/纳管，再选择
  `projectVolumeId`。
- 创建/更新部署配置在同一 PostgreSQL 事务中对数据卷行 `FOR UPDATE`，校验项目、
  集群、卷模式、访问模式和独占约束后创建 `reserved` 挂载记录。
- Worker 下发工作负载后从 Pod/PVC 权威回读挂载关系，成功后使用 CAS 更新为
  `active`；失败保留 `reserved` 和稳定错误码，便于修复后重发 Release。
- 从部署配置移除挂载或删除部署配置时，先标记 `release_pending`，Worker 确认工作负载
  已不再引用后删除关系；即使部署从未成功，删除目标也必须释放 `reserved`。
- 应用/部署配置删除预览返回关联 ProjectVolume。默认仅解绑并让卷回到
  `available`；用户显式选择删除的非共享托管卷另行投递 Volume Delete，不在应用清理
  事务中直接删 PVC。
- 删除 `DataRetentionEnabled`、`DataCapacity`、`DataMountPath`、`DataStorageClassName`、
  `DataAccessMode`、`DataVolumeMode` 等旧目标级存储字段；规格收敛到每个 ProjectVolume。

## 8. 对象存储与归档格式

### 8.1 VolumeTransferStore

新增 `internal/provider/volumestore` 接口：

```go
type Store interface {
    CreateMultipart(ctx context.Context, key string) (uploadID string, err error)
    WritePart(ctx context.Context, key, uploadID string, partNumber int, body io.Reader, size int64) (etag string, err error)
    CompleteMultipart(ctx context.Context, key, uploadID string, parts []CompletedPart) error
    AbortMultipart(ctx context.Context, key, uploadID string) error
    Head(ctx context.Context, key string) (ObjectInfo, error)
    ReadRange(ctx context.Context, key string, offset, length int64) (io.ReadCloser, error)

```

首个生产实现为 S3-compatible provider，bucket 必须私有，默认开启服务端加密，对象 key
只使用不可猜测 ID，不含项目名、文件名或用户输入。凭据进入 Secret Store/进程配置，

```env
VOLUME_TRANSFER_S3_ACCESS_KEY_ID=...
VOLUME_TRANSFER_S3_SECRET_ACCESS_KEY=...

VOLUME_TRANSFER_MAX_BYTES=100Gi

VOLUME_TRANSFER_SPOOL_MAX_BYTES=2Gi
VOLUME_TRANSFER_SPOOL_MIN_FREE_BYTES=1Gi
VOLUME_TRANSFER_SPOOL_ORPHAN_AGE=24h

```

对象存储未配置时，数据卷创建、列表、挂载和删除仍可用；Import/Export 端点稳定返回
`503 volume_transfer.store_unavailable`，不降级回原有五分钟直连流。

### 8.2 归档格式

Filesystem 导出为 `tar.gz`，根目录包含：

```text
luna-volume-manifest.json
data/
```

Manifest 固定 `schemaVersion: 1`，包含 volumeMode、format、导出时间、逻辑字节数、文件数、
完整数据 SHA-256 和 consistency mode；不包含项目名、用户名、集群地址、Secret 或内部
URL。外部普通 `tar.gz` 可以没有 Manifest，导入后由平台生成内部摘要。

Block 导出为 `raw.zst`，另提供同名 `.manifest.json` 资源元数据；导入前必须显式选择
`volumeMode=Block`，不按文件归档自动猜测。

## 10. 稳定错误码

| 错误码 | HTTP | 语义 |
| --- | --- | --- |
| `volume.not_found` | 404 | 数据卷不存在或不可见 |
| `volume.cluster_unavailable` | 503 | 运行集群无法观察/执行 |
| `volume.claim_not_found` | 404 | 待引用/纳管 PVC 不存在 |
| `volume.ownership_conflict` | 409 | PVC 已属于其他项目或工作负载 |
| `volume.incompatible_cluster` | 409 | 数据卷与部署目标不在同一集群/Namespace |
| `volume.binding_conflict` | 409 | 访问模式、独占或读写关系冲突 |
| `volume.in_use` | 409 | 存在活动挂载或 Transfer |
| `volume.capacity_shrink_forbidden` | 409 | 请求缩容 |
| `volume.snapshot_unsupported` | 422 | 集群/StorageClass 不支持 Snapshot |
| `volume.snapshot_required` | 409 | 使用中卷的默认导出需要 Snapshot |
| `volume_transfer.store_unavailable` | 503 | 暂存对象存储不可用 |
| `volume_transfer.spool_busy` | 429 | 当前 API 副本的落盘 byte budget 已满 |
| `volume_transfer.spool_unavailable` | 503 | 专用 spool 目录或容量探测不可用 |
| `volume_transfer.spool_insufficient_storage` | 507 | spool 磁盘无法保留要求的安全余量 |
| `volume_transfer.offset_mismatch` | 409 | 上传 offset 不一致 |
| `volume_transfer.part_in_progress` | 409 | 相同 offset 的同内容分片正在由其他副本写入 |
| `volume_transfer.part_conflict` | 409 | 相同 offset 已预留给不同 size/checksum |
| `volume_transfer.chunk_checksum_mismatch` | 460 | 分块校验和不一致 |
| `volume_transfer.checksum_mismatch` | 422 | 完整归档校验和不一致 |
| `volume_transfer.archive_unsafe` | 422 | 归档包含越界/特殊文件 |
| `volume_transfer.capacity_exceeded` | 422 | 展开后数据超过目标容量 |
| `volume_transfer.expired` | 410 | 上传、归档或票据已过期 |
| `volume_transfer.state_conflict` | 409 | Transfer 已进入不兼容终态 |

生产响应只返回 `code/error/requestId`，开发模式可附带 `detail`。对象存储原始错误、
Kubernetes API 错误、解包路径和 Job stderr 不得进入生产响应。

## 11. Worker 任务和恢复

新增 Asynq 类型：

| Task | Queue | 负载核心字段 | 幂等/重试 |
| --- | --- | --- | --- |
| `volume:provision` | `deploy` | envelope, volumeId, projectId, actorId | 按 volumeId 唯一，10 次 |
| `volume:import` | `deploy` | envelope, transferId, volumeId, projectId, actorId | 按 transferId 唯一，5 次 |
| `volume:export` | `deploy` | envelope, transferId, volumeId, projectId, actorId | 按 transferId 唯一，5 次 |
| `volume:delete` | `deploy` | envelope, volumeId, projectId, actorId | 按 volumeId 唯一，10 次 |
| `volume:reconcile` | `light` | envelope, optional volumeId | 周期扫描，分页 100 |
| `volume-transfer:cleanup` | `light` | envelope, optional transferId | 周期清理，分页 100 |

所有状态迁移使用数据库 CAS/row lock，不依赖进程内 mutex。Worker 启动时只扫描已超时的
`provisioning/deleting/queued/running`记录生成有界重试任务，不对整表无分页扫描。任务取消必须
取消 Job，但清理 Job/Snapshot/临时 PVC 使用明确注释的独立限时 Context。

Import 成功的权威回读是：PVC 存在且归属标签正确，Transfer Job 终态成功，完整
SHA-256 一致。Export 成功的权威回读是：对象存储 Head 大小/ETag 可读，Transfer Job 终态
成功，转换端回报的 SHA-256 一致。仅任务投递成功不得标记业务成功。

取消尚未完成的 Import 会删除临时对象、部分写入 PVC 和待导入 ProjectVolume；不保留
一个内容不明的“空白卷”。失败 Import 保留错误状态和未过期归档以便显式重试；过期清理后
只能重新上传。

## 12. 计费与配额

- `managed` ProjectVolume 按 Kubernetes 当前页/批次实时回读的 PVC capacity 计算
  `storage.gib_day`，无论是 `available`、`reserved` 还是 `in_use`都计费。
- `referenced` 数据卷不对申明容量计费，但 Transfer 产生的临时对象存储/流量可使用独立
  `storage.transfer_gib`计量。
- 存储费用资源 ID 改为 `project_volume_id + hourly_window`，移除当前按 deployment target 结算的
  口径，避免卷解绑后停止计费。
- 创建空白卷、纳管、Snapshot 恢复和 Import 完成前都检查项目空间管理容量配额；
  扩容检查 delta，并在 PostgreSQL 事务内预留配额，失败/取消补偿释放。
- 费用不足时 API 创建 Import/Volume 直接返回稳定计费错误；运行中导入如因实际展开量
  超配额则进入可见失败终态，不静默丢数据。

## 15. 迁移与上线顺序

产品最终一次性收敛到新模型，但生产数据迁移使用 expand/backfill/switch/contract，避免不可恢复
的单次破坏性发布。

### A. Expand

- 新增 `000066_project_volume_center` 迁移，创建四张新表、约束和索引，不删旧表/字段。
- 上线新 Model、Repository、Service、Provider 和只读差异检查器；旧路径暂不改读取源。
- 新写入临时双写旧/新结构，双写代码必须标注删除条件和最迟版本，不得形成长期
  兼容层。

### B. Backfill

- `retained_volumes` 转为 `source_kind=retained, ownership_mode=managed`，来源应用/目标保留为
  nullable 追溯字段。
- 从部署配置 JSON 和稳定 PVC 命名生成托管 ProjectVolume；`existingClaim` 生成
  `ownership_mode=referenced`；`emptyDir` 只生成 mount。
- 使用可重入的 `cmd/migrate-volume-center` 按项目空间和部署目标分页迁移，通过 Kubernetes
  实时回读验证 cluster/namespace/claim/labels；无法观察时记录稳定待修复项，不猜测
  成功。
- 迁移 ID 使用旧资源主键的稳定 hash 生成 `pvol_`/`dvmt_`，重跑不会创建重复资源。

### C. Switch

- 门禁要求：旧托管 PVC 和保留卷都存在新表，挂载数和容量对账一致，无待修复项，
  随机抽样从 Kubernetes 回读通过。
- API、Worker、计费、Web、CLI 和 Agent 在同一个候选版本切换到新契约；切换后不存在
  旧读取 fallback。
- 停止旧部署数据卷写入，移除旧 API 路由和双写。

### D. Contract

- 新增后续迁移，删除 `retained_volumes`、部署目标旧存储字段和旧索引。
- 删除 `cmd/migrate-volume-center` 和临时双写/差异检查代码。
- 新契约完整验收后，从 `docs-internal/README.md` 删除本方案，只将仍需长期维护的规则
  提取到产品边界、可观测标准和公开文档。

回滚边界：Expand/Backfill 可回滚新代码且保留新表；Switch 前必须完成数据库备份。Switch
后只能回滚应用版本到同时理解新表的候选版本，不允许回到只写旧 JSON 的版本。Contract
为明确不可逆迁移，执行前再做一次对账和备份。

## 17. 验收与测试矩阵

### 17.1 合同与单元测试

- 迁移 SQL 从 fresh database 和 `000065` 历史 schema 升级，检查 FK、CHECK、部分唯一索引和回滚声明。
- PostgreSQL 真实并发测试：两个目标同时绑定 RWO 卷只能一个成功；重复幂等键不重复创建
  PVC/Transfer/账单。
- API 契约：默认分页、100 上限、排序白名单、筛选、`If-Match`、稳定错误码和生产无
  detail。
- 归档安全：路径穿越、绝对路径、symlink/hardlink 越界、device node、压缩炸弹、超容量、
  校验和不一致和取消。
- TUS：正常多分块、offset 冲突、分块重放、API 多副本、过期、最后一块和完整校验和。
- 前端：服务端分页选择、集群切换清理旧选择、上传恢复、失败重试、下载过期、权限和 i18n。
- Agent：数据卷查询/创建/删除在相似工具中进入前 8，协议适配端点永不下发给模型，
  Scope 和后端策略一致。

### 17.2 端到端场景

1. 创建空白 Filesystem 卷 → 在部署配置绑定 → Release 成功 → Kubernetes PVC/Pod 回读
   `in_use` → 删除部署配置 → 卷回到 `available`。
2. 上传多分块 `tar.gz` 中断后续传 → Worker 安全解包 → SHA-256/PVC 回读成功 → 挂载
   到应用并验证抽样文件。
3. 导出未使用卷 → 断点下载 → 校验和一致 → 将该归档导入新卷 → 抽样数据一致。
4. 使用中卷 `auto` 导出 → CSI Snapshot → 临时 PVC → 归档 → 清理 Snapshot/PVC/Job/Secret；
   不支持 Snapshot 时返回稳定拒绝，显式 `live` 另行验收。
5. 引用外部 PVC 后删除平台记录，底层 PVC 仍存在；纳管模式则写入归属标签并进入
   托管计费。
6. Owner/Admin/Developer/Viewer、跨项目 ID、跨集群、冲突 PVC 标签、撤销 OAuth grant、
   过期 Session/OAuth Grant 和票据重放均按权限表 fail closed。
7. API 取消、Worker 重试、Job 中断、对象存储短暂不可用、集群不可达和 API 重启后，
   Transfer 可恢复或进入明确终态，无长期 `running`。
8. 计费窗口覆盖 `available/reserved/in_use` 托管卷，同一小时不重复扣费；余额/配额不足
   时 UI、CLI 和 Agent 均展示同一稳定错误。
9. 一条 Web → API → PostgreSQL/Redis/Asynq → Worker → Kubernetes Job → Internal API → Object Store
   成功链路和一条失败链路在 Tempo/Loki/Prometheus 中具有正确父子关系和稳定结果，
   遥测中不出现归档内容、路径、凭据或对象 URL。

## 18. 完成定义

同时满足以下条件才能标记本方案完成：

- 旧保留卷、托管 PVC 和 `existingClaim` 已迁移，旧表/字段/路由/双写已删除。
- 项目空间数据卷列表、详情、创建、引用/纳管、Snapshot 恢复、挂载、解绑、导入、
  导出、删除、计费和配额全部通过真实上游回读验收。
- OpenAPI、Web types/client、Worker payload、CLI、Agent Tool/Scope/Skill、中英文公开文档和 i18n
  一致。
- 高危操作的 RBAC、实时会话、票据、幂等、审计、生产错误边界和取消/重试终态通过。
- 存储结算覆盖未消费托管卷，不因删除应用或解绑而停止计费。
- 前端关键路径浏览器验收通过，数据卷选择不再受前 100 条限制，资源切换不展示旧观察。

## 19. 明确不支持的边界

- 不允许用户上传任意 PV/PVC YAML 或直接指定 CSI `volumeHandle`；外部数据通过归档、
  Snapshot 或同 Namespace 已有 PVC 进入。
- 不声称不同 CSI 驱动间的 Snapshot/PV 原生可移植；跨集群和跨驱动迁移使用
  Filesystem `tar.gz` 或 Block `raw.zst`。
- 不在 PostgreSQL、Redis、前端 LocalStorage 或审计日志中保存卷内容。
- 不提供跳过归属冲突、容量、归档安全、校验和、权限或审计的 `force` 参数。
