# 项目空间与应用

## 项目空间工作流

- 在要求用户输入项目 ID 前，先用 `listProjects` 列出或比较项目空间。省略 `visibility` 即默认
  `related`；即使当前用户是平台管理员，也只有在其明确要求全局查找、盘点或跨项目比较时才传
  `visibility: all`。不得再使用 `scope` 或 `mine`。
- `getDashboard` 同样默认 `visibility: related`；只有平台管理员明确要求全局看板时才使用
  `visibility: all`，并把返回的项目、活动、待处理项和资源就绪度作为同一范围的权威回读。
- 选择项目空间、应用或模板前遵守根 Skill 直接索引的 `resource-resolution.md`。同类有效
  候选只有一个时直接采用；用户明确要求查看其他候选或新建时再进入选择或创建流程。
- 创建项目空间时，收集显示名称和标识符；仅在相关或必填时收集描述、限制、命名空间策略和控制台偏好。
- 选择目标项目空间时，用包含可信项目 ID 的 `send_message` 值返回项目选项；后续支持
  `projectId` 的列表调用必须用该 ID 进一步缩小 `visibility` 结果。
- 处理成员与角色时，明确项目空间、用户、目标角色，以及是在新增、变更还是移除访问权限。
- 将归档、删除、所有权转移、降低配额和移除成员视为潜在高风险操作，由平台策略请求批准。
- 创建后回读项目空间 ID、名称、标识符和当前用户角色，再继续创建应用或成员。
- 更新名称、描述、命名空间策略、控制台或计费归属前，先读取当前值并只提交用户明确
  要修改的字段；标识符不可变时不得承诺修改。
- 添加成员前搜索平台用户候选，不把任意邮箱当作已存在用户。角色变更或移除后回读
  成员列表；所有权和最后一个 Owner 相关限制由平台最终校验。
- 删除项目前先读取应用、部署配置、网关、服务关系和计费影响；删除受理后回读直到
  业务记录与受管资源达到删除终态。

## 应用工作流

- 明确目标项目空间、应用创建来源和预期交付路径。
- 区分部署应用市场模板、从源码构建和部署现有镜像。
- 用户要检查、部署、重启或配置现有应用时，应复用该应用，不要创建重复应用。
- 创建前收集名称、标识符和来源所需的最少参数。可选的运行时、网关和扩缩容问题留到对应阶段再询问。
- 用户选择应用或项目空间时使用 `send_message`；只有用户要求检查资源时才跳转。
- 用户操作现有应用时先读取应用、部署配置和拓扑，区分修改应用展示信息、修改部署
  配置、创建 Release、重启和删除。
- 应用创建后回读真实 ID 和来源；仅创建应用不会自动生成部署配置、构建或 Release。
- 删除应用前检查部署配置、服务引用、网关、历史 Release 和删除影响预览。删除应用只解除
  DeploymentVolumeMount 并清理运行资源，不会删除 ProjectVolume 或底层 PVC；不得把删除
  应用描述为已经删除数据。
- 用户新建部署配置或安装持久化模板时，先用项目数据卷工具查询同项目空间、同集群
  可用的 ProjectVolume，再通过 `projectVolumeId` 建立挂载。需要使用已有 PVC 时，应先在项目数据卷
  中心完成引用或纳管，不得把 PVC 名称直接作为部署输入。

## 运行配置集、服务关系与拓扑

- 项目空间运行配置集用于多个部署配置共享值；创建、更新、删除时明确跟随引用与快照
  的差异，并在变更后回读引用关系。
- 服务绑定会影响源部署配置，只有源应用创建新 Release 后才进入运行态；仅记录的拓扑
  边只用于说明关系，不得声称已经建立网络连接。
- 诊断服务关系时检查源/目标部署配置、集群、Service、端口、EndpointSlice 和
  NetworkPolicy；拓扑图存在一条边不等于流量可达。

## 应用市场工作流

- 使用 `listAppTemplates` 按用户描述、关键词或分类搜索平台模板摘要。列表返回名称、分类、描述、版本、默认资源、强类型 `dataVolumes` 声明和参数数量，不包含完整参数定义；用户选定某个模板后，必须用 `getAppTemplate` 读取完整 `values` 与 `dataVolumes`，再据此生成安装表单。不要在浏览或比较多个模板时逐个调用 `getAppTemplate`。
- 仅浏览搜索结果时使用 `mode: presentation` 的 `candidates` 卡片展示名称、用途、
  版本、来源、默认资源和可信参数定义，不要把原始 JSON 倾倒给用户。
- 用户正在安装并需要选择模板时，使用 `mode: interactive`。2～5 个候选时每个模板
  一张卡并提供“选择此模板”的动作；候选超过 5 个时使用 `form` 的 `select` 字段和
  “继续配置”提交动作。不得用不可点击的 `item_list` 要求用户选择。
- 安装意图已经明确且过滤后只有一个兼容模板时直接采用该模板，继续收集其真实必填参数，
  不生成只有一个候选的模板选择卡。
- 执行前询问目标项目空间，使用项目选择项，不要使用项目页面链接代替选择。
- 当模板 `dataVolumes` 含 `sourceType: projectVolume` 时，必须先按目标项目空间和集群列出已就绪的数据卷，让用户显式选择真实 `projectVolumeId`；不得填写占位 ID、降级为 `emptyDir`，也不得在未挂载持久卷时继续安装。
- 将模板选择、目标选择、参数收集、审阅、执行和验证分成清晰阶段。
- 模板候选卡、配置表单和部署确认卡只完成选择与输入阶段，不能作为安装或部署完成
  的证据。所有参数齐全后，应继续调用真实安装 operation，而不是用展示卡结束工作流。
- 只有当前工具列表存在安装 operation ID 时，安装按钮才能使用 tool action；否则使用
  `send_message` 保留用户选择并明确说明当前不能直接执行，不能伪造安装动作。
- 没有安装写工具时应明确说“尚未安装”，并说明当前只能完成模板检索与参数整理；
  不得生成“部署确认”“安装回执”“部署进度”等容易被理解为已经执行的展示卡。
- 不得暗示打开应用市场就完成了部署。

## 验证

- 安装工具返回成功后，至少回读应用与安装记录，确认目标项目空间、模板、应用名称和
  非敏感配置一致。
- 若立即部署，还要继续读取 Release 或工作负载状态。`queued`、`pending`、
  `deploying` 只能说“已提交”或“部署中”，达到就绪终态后才能说“部署完成”。
- 创建或更新后报告新资源的可信 ID、实际状态和下一个可执行阶段；没有回读工具时明确
  说明无法独立验收，不得把请求受理当作完成。
- 项目空间验收：资源存在、标识符和成员角色符合目标；涉及删除时确认资源已不存在。
- 应用验收：应用属于正确项目空间且来源正确；用户目标包含运行时，还必须继续验收
  部署配置、Release 和工作负载，不能停在应用记录创建成功。
