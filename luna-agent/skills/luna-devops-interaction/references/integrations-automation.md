# 集成、关系与自动化

## Git 与 Webhook 自动化

- 区分连接 Git Provider、授权账号、绑定仓库、创建 Webhook 和重新配置 Webhook。
- 先读取 Provider、账号、仓库和现有绑定，再让用户选择；不得要求手填账号或仓库 ID。
- 建立绑定后回读账号、仓库、默认分支和绑定状态。启用 Webhook 时验证远端配置或平台
  返回状态，再通过一次受控测试事件或真实 push 检查是否产生 BuildRun。
- Webhook 创建请求成功但后续没有 BuildRun 时，依次检查签名、事件类型、分支策略、
  远端投递记录和平台事件。

## 项目空间钩子

- 先区分可复用钩子定义和部署配置中的阶段绑定。只创建脚本库不会自动执行。
- 收集名称、脚本或命令、运行镜像、超时、环境变量和适用阶段；Secret 使用引用。
- 绑定到构建前后、镜像推送前后或部署前后时，明确失败是否阻断主流程。
- 执行后读取 HookRun 与日志。只有钩子成功且后续主流程继续时，才能说明对应阶段完成。

## 服务关系与拓扑

- 区分会改变运行配置的“服务引用”和只做文档表达的“仅记录关系”。
- 创建服务引用前确认源/目标应用、部署配置、集群和端口；首版只在平台支持的同项目、
  同集群范围内建立。
- 不把数据库密码或 Token 拼入服务地址；敏感连接参数使用 Secret。
- 创建后回读关系与项目/应用拓扑。服务引用只有在源应用创建新 Release 后才进入运行
  Pod，关系记录保存成功不等于流量已经连通。
- 验收服务引用时检查目标 Service、端口、EndpointSlice、NetworkPolicy 和源应用新
  Release；被引用资源删除前先移除或停用关系。

## 通知渠道、模板与规则

1. 选择渠道类型或预设，收集非敏感配置，并通过受控 Secret 字段保存 Token/密码。
2. 创建渠道后调用测试操作；测试成功只证明渠道可达，不证明规则会命中。
3. 创建或确认模板，检查变量名、目标协议和详情链接。
4. 创建规则，明确事件类型、级别、项目空间、应用、部署配置和渠道。
5. 触发一条匹配事件，读取投递记录、尝试次数、状态和脱敏错误。

验收：渠道测试成功，规则和模板回读一致，真实匹配事件只生成预期投递且最终成功；
网络错误、429、5xx 可以按策略重试，确定性配置或模板错误应先修正再重试。

## 运行配置集与构建变量集

- 区分项目空间公共运行配置、部署级覆盖、构建变量集和 Secret 变量。
- 新建或更新前读取引用关系，避免删除后造成不可预期配置缺失。
- 公共配置明确“跟随引用”与“使用快照”；修改公共配置后，不得声称运行中的 Pod
  已经变化，必须创建新 Release 才能验收生效。
- 删除变量集或配置集后回读部署配置引用，确认平台已经清理或拒绝无效引用。

## 自动化闭环

任何自动化都按以下顺序验收：

```text
定义/连接已保存
  -> 触发条件已绑定
  -> 产生一次真实或受控测试事件
  -> 平台创建运行或投递记录
  -> 运行到达可解释终态
  -> 结果关联回原项目、应用或部署配置
```

只看到配置存在、按钮点击成功或队列受理都不能说明自动化已经工作。
