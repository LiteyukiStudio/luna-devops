# 网关、域名、DNS 与证书工作流

## 收集输入

- 按需明确项目空间或应用、服务端口、主机名、路径匹配、协议、TLS 意图，以及目标网关或集群。
- 网关、集群、域名后缀和证书候选遵守根 Skill 直接索引的 `resource-resolution.md`；唯一
  兼容候选直接采用，多候选或具有实质 TLS 权衡时再交互。
- 要求标识符前，先发现现有路由、域名、网关、服务和证书。
- 校验主机名确实是主机名而不是完整 URL；区分根域名、子域名、通配域名和路径路由。
- 服务端口必须来自目标部署配置的真实 Service；不存在时先恢复或发布工作负载，不让
  用户凭记忆填写 Kubernetes Service 名称。
- 域名后缀优先来自运行集群配置；自定义完整域名先执行冲突与可用性检查。

## 规划变更

- 区分创建路由、修改路由规则、绑定域名、配置 DNS 和签发或续期证书。
- 相关时解释 DNS 前置条件和传播过程；除非工具确认，否则不得声称外部 DNS 已经改变。
- 避免竞争路由和含糊的主机或路径匹配。提出可能冲突的变更前先检查现有路由。
- 将删除路由、更换证书和流量切换视为有影响的操作。
- TLS 模式必须与真实链路匹配：上游代理终止、Gateway 使用已有 TLS Secret、
  cert-manager HTTP-01 或集群通配符证书。不得假定平台会创建 Issuer。
- 代理链存在协议覆盖时明确 `X-Forwarded-Proto` 与可信代理要求，尤其是 OIDC、
  Logto 等依赖外部 URL 的应用。

## 验证

- 有对应工具时，检查路由就绪状态、后端或服务解析、证书状态、Issuer 状态、DNS 观测和相关运行时事件。
- 区分 DNS 传播、Issuer Challenge、证书、网关接纳、后端就绪和应用响应失败。
- 路由创建成功不代表应用健康或已经可以公网访问。
- 只有用户要检查路由或证书页面时才提供跳转；实际变更应提供操作选项。
- 创建或更新后回读 HTTPRoute 条件，至少核对 Accepted、ResolvedRefs、Programmed、
  后端 Service/端口和证书状态；有 DNS 观测能力时再检查解析。
- 用户目标是“可以访问”时，还要验证应用后端就绪和外部响应；只下发 HTTPRoute 不算完成。
- 删除路由后确认 HTTPRoute 和相关证书引用进入预期终态；不要声称外部 DNS 记录已删除，
  除非 DNS 工具明确确认。
