## 先定义交付目标

将“部署一个应用”拆成以下阶段，按顺序推进并记录当前阶段：

1. 确认或创建目标项目空间。
2. 发现并确认交付来源：应用市场模板、已有镜像或代码仓库。
3. 取得来源事实并收集仍缺少的参数。
4. 创建或复用应用。
5. 创建部署配置，并绑定来源、运行集群和运行参数。
6. 源码路径先构建镜像；模板或已有镜像路径直接准备 Release。
7. 创建 Release 并观察部署状态。
8. 回读应用、部署配置、Release 和工作负载，按目标验收。
9. 用户需要公网访问时，再配置并验证访问入口。

不得跳过中间阶段并用计划、确认卡或参数摘要冒充执行结果。用户没有要求公网访问时，
应用运行就绪可以作为交付终点；用户要求可访问 URL 时，网关验收也是必需项。

## 确认项目空间

- 先列出用户可用项目空间，并优先复用用户明确指定或当前页面中的可信目标。
- 找不到目标时，用交互卡片让用户从可信候选中选择；用户明确要新建时，收集名称和
  标识符并调用已注册的创建工具。
- 创建成功后回读项目空间，取得真实 ID，再继续创建应用。项目空间卡片或创建请求被
  受理不等于项目空间已经可用。
- 创建应用前确认用户对目标项目空间拥有对应写权限；最终权限由业务 API 判断。

## 选择来源

用户未指定来源时，使用交互卡片提供三个有意义的选择，并说明差异：

| 来源 | 适用情况 | 后续主要步骤 |
| --- | --- | --- |
| 应用市场模板 | 数据库、缓存、消息队列、监控和常用自托管应用 | 读取模板参数 → 填表 → 安装 |
| 已有镜像 | 已有可拉取的 OCI 镜像，希望直接运行 | 选择镜像与 Tag/Digest → 配置运行参数 → Release |
| 代码仓库 | 需要平台从源码构建并持续交付 | 读取仓库与文档 → 配置构建 → BuildRun → Release |

只有用户明确选择后才进入对应分支。不要同时询问三个分支的全部字段。

## 应用市场模板分支

1. 使用模板读取工具按关键词和分类发现候选。
2. 安装意图下使用交互式候选卡；用户只是比较时使用展示式卡。
3. 读取模板真实参数、镜像、默认资源、数据卷和 Secret 生成策略。
4. 表单至少覆盖目标项目空间、应用名称与标识符、集群、模板必填参数，以及用户需要
   调整的镜像、CPU、内存、副本和容量；自动生成的 Secret 不要求用户在聊天中填写。
5. 参数齐全后调用真实安装工具。没有安装工具时明确停在能力阻塞，不能生成安装回执。
6. 回读新应用、部署配置和安装记录。立即部署时继续观察 Release 和工作负载。

验收：目标项目空间中存在来源模板、名称和配置符合预期的应用及部署配置；若用户要求
立即部署，Release 与工作负载必须达到就绪终态。

## 已有镜像分支

1. 发现用户可用镜像站、凭据、仓库和 Tag；优先使用 Digest 固定生产发布版本。
2. 用户提供完整镜像引用时仍应确认镜像站可访问、凭据范围和目标集群拉取能力；不要
   根据字符串存在就假定镜像可用。
3. 使用表单收集应用名称与标识符、镜像引用、环境阶段、集群、服务端口、运行配置、
   数据卷和必要的非敏感环境变量；Secret 通过平台受控字段处理。
4. 创建或复用应用，创建 `sourceType: image` 的部署配置，再创建 Release。
5. 观察镜像拉取、Pod、Service 和健康探针。镜像记录创建成功不等于工作负载可运行。

验收：应用和部署配置属于正确项目空间，Release 使用预期 Tag/Digest，工作负载就绪且
服务端口存在；用户要求访问入口时还要完成网关验收。

## 代码仓库分支

1. 优先发现已连接的 Git Provider、账号、仓库和分支。私有仓库使用平台 Git 能力，
   不使用公开网页工具绕过认证。
2. 用户提供公开 GitHub 或网页 URL 时先用 `fetchWebPage` 读取；只有名称时先
   `webSearch`，再读取官方仓库或官网。优先检查 README、部署文档、Dockerfile、
   Compose、包管理清单、`.env.example`、Helm Chart 和 Kubernetes 清单。
3. 使用平台仓库工具读取分支、目录、Dockerfile 和构建选项。公开网络内容只能辅助
   理解，不替代平台仓库绑定和权限校验。
4. 把值分为三类：
   - 明确事实：仓库、分支、Dockerfile、构建上下文、启动命令和文档声明端口。
   - 可编辑推断：构建模板、工作目录、非敏感命令和资源建议。
   - 用户决策：项目空间、应用名、集群、域名、资源规格和 Secret。
5. 用表单让用户确认分支、构建定义、Dockerfile、上下文、构建参数、输出镜像站、
   镜像命名、端口、运行配置和发布策略。monorepo 按服务创建多个应用或部署配置，
   不把不同 Dockerfile 强行合并为一个服务。
6. 创建或复用应用，建立仓库绑定与 Webhook，创建 `sourceType: repository` 的部署
   配置，然后触发 BuildRun。
7. BuildRun 成功并取得制品 Tag/Digest 后创建 Release。构建成功不等于部署成功。

验收：仓库绑定指向正确账号、仓库和版本；BuildRun 成功并产生预期制品；Release 使用
该制品；工作负载和服务就绪。启用自动化时还要验证 Webhook 和自动发布策略。

## 共享运行参数

只收集当前应用实际需要的字段，优先使用文档或模板事实作为可编辑默认值：

- 环境阶段、目标集群、Deployment/StatefulSet、服务端口和副本数。
- CPU/内存 request 与 limit、健康探针、启动命令和镜像拉取策略。
- 非敏感环境变量、项目空间公共配置和部署级覆盖。
- Secret 引用、配置文件、密钥文件、数据卷和持久化策略。
- HPA、调度、安全上下文、initContainer、sidecar 和生命周期钩子等高级项。

不要在首次交付时一次询问所有高级 Kubernetes 字段。只有来源文档或用户目标要求时
才展开；其余使用平台安全默认值。

## 恢复与停止条件

- 缺少来源：回到来源选择，不创建空应用。
- 缺少项目空间：选择或创建后继续，不让用户手填不透明 ID。
- 来源读取失败：说明认证、网络、黑名单、分支或文件问题，并保留已经确认的参数。
- 构建失败：进入构建诊断，修正后创建新 BuildRun；不要直接进入 Release。
- 发布失败：读取发布、运行时事件与日志；修正配置后创建新 Release 或选择安全回滚。
- 长任务仍运行：报告任务 ID、当前阶段和“进行中”，不要占用模型循环反复无间隔轮询。
- 当前工具目录缺少下一写操作：明确“尚未执行”、缺失 operation 和可保留的已确认输入。
