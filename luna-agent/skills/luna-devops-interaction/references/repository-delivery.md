## 把一句话目标展开为闭环

用户给出 GitHub/Git 仓库并要求部署时，默认目标不是“解释怎么部署”，而是在用户权限和
已注册工具允许的范围内完成以下闭环：

1. 确认仓库身份、目标版本和可读取性。
2. 阅读部署说明，同时检查真实目录、构建清单和运行入口。
3. 识别单体、多服务、数据库、缓存、队列、初始化或迁移依赖。
4. 评估各服务是否存在经过验证的官方镜像；可用时建议镜像直部署，否则保留源码构建。
5. 选择或创建项目空间与应用，收集无法安全推断的参数。
6. 为源码服务建立仓库绑定和构建配置，为镜像服务建立镜像来源部署配置。
7. 构建每个源码服务，取得不可变制品，再为所有服务创建 Release。
8. 验证工作负载、依赖、服务端口和用户要求的访问入口。

只有用户明确要求“只分析”“只生成方案”时才停在分析阶段。不要要求用户先写出上述步骤。

## 按证据层级读取仓库

先读取能确定仓库结构的最小集合，再按发现结果深入，不要无目的遍历所有文件：

1. 仓库元数据：默认分支、目标 commit/tag、根目录清单、子模块和大文件提示。
2. 人类说明：README、部署文档、运维文档、示例 Compose/Helm/Kubernetes 清单。
3. 可执行事实：Dockerfile、Compose、包管理清单、语言模块文件、构建脚本、入口代码、
   `.env.example`、迁移目录、健康检查和 CI 中实际执行的命令。
4. 服务局部事实：每个服务目录的 Dockerfile、依赖清单、配置样例、端口和启动入口。
5. 必要外部资料：只有仓库内容引用特定框架或外部安装文档且当前事实不足时才读取。

公开仓库优先使用平台 Git 内容工具读取目录和文件；网页读取适合 README、官网和外部
文档。私有仓库必须使用用户已连接的 Git 账号和仓库能力，不得用公开网络工具绕过认证。

每个结论保留来源文件路径和目标版本。分支变化后，旧文件结论不再视为当前事实。

## 选择部署资料基线

目标运行环境为 Luna DevOps/Kubernetes，且项目同时提供同版本的 Kubernetes/Helm 与
Docker/Compose 部署资料时，优先以 Kubernetes/Helm 资料确定工作负载类型、服务端口、
探针、持久化、Secret/ConfigMap、初始化任务和资源依赖；再用 Dockerfile、Compose 和
环境变量样例补充服务拓扑、镜像、启动命令及缺失参数。Compose 中的开发专用 bind mount、
热更新、固定主机名和宿主机端口不得直接转换为生产配置。

这是一项有条件的证据优先级，不是机械规则。Kubernetes/Helm 资料与目标版本不一致、已
废弃、仅适用于特殊集群或缺少完成目标所需配置时，说明依据并改用更新且可执行的 Docker/
Compose 或源码事实；必要时把真实冲突交给用户选择，不要把不同资料静默拼成无法验证的配置。

## 先评估官方镜像

仓库或官方文档声明 Docker Hub、GHCR 等 OCI 镜像时，先按照
`delivery-orchestration.md` 的“评估官方镜像捷径”逐服务验证来源、版本、Manifest、可拉取性、
维护状态和运行能力。验证通过时建议使用官方镜像直接交付；这不是强制选择，用户明确要求
源码构建时继续源码流程。验证不通过或官方镜像不能满足目标时，再使用下面的仓库事实生成
源码构建配置，不要因为发现过镜像就停止交付。

## 核对 README 与真实结构

README 是线索，不是最终执行契约。按以下优先级处理冲突：

1. 当前目标 commit 中实际存在的构建文件、依赖清单和入口代码。
2. 同版本的部署清单、自动化脚本与 CI 实际命令。
3. 同版本 README 和部署文档。
4. Release 说明、Issue、搜索摘要和模型常识。

发现冲突时不要静默选择：说明冲突文件和采用依据；若两种方式都可能成立，用交互式卡片
让用户选择。常见冲突包括：

- README 指向已不存在的目录、脚本或环境变量。
- Dockerfile 的工作目录、端口或构建阶段与 README 不一致。
- Compose 只面向本地开发，含 bind mount、热更新、固定主机名或开发数据库。
- 示例镜像、Tag、Node/Go/Python 版本已过期。
- CI 使用与 README 不同的构建命令、子目录或生成步骤。
- `.env.example` 缺少代码中实际必填的变量，或仍包含废弃变量。

不能确认的值不得伪装成文档事实。把它标记为可编辑推断，或留给用户选择。

## 识别服务和依赖

为每个可独立构建或运行的组件建立服务清单：

- 服务名、源码目录、语言/框架、构建上下文、Dockerfile 或平台构建方式。
- 构建命令、启动命令、监听地址、容器端口、健康检查和静态产物。
- 必填与可选环境变量；区分普通值、Secret、内部服务引用和构建期变量。
- 数据库、缓存、对象存储、队列、邮件、OAuth 等依赖及其版本约束。
- 数据库迁移、种子数据、一次性初始化、启动顺序和失败重试语义。
- 持久卷、写目录、用户权限、资源建议和水平扩展限制。

monorepo 不等于单应用。满足任一条件时优先拆成多个应用或部署配置：不同 Dockerfile、
不同生命周期、不同端口、独立扩缩容、独立发布或不同运行时依赖。共享源码目录不能作为
强行合并服务的理由。

前后端项目还要检查：前端构建时还是运行时注入 API 地址、后端 CORS/公开 Base URL、
反向代理路径、SSR 与静态站点差异。数据库项目要确认驱动格式、迁移执行方、连接池和
Secret 传递方式，不把示例密码带入配置。

## 决定依赖复用边界

按根 Skill 直接索引的 `service-dependency-planning.md` 为每个数据库、缓存、队列、对象
存储、搜索、向量库、可观测和平台集成选择明确归属。不得只按组件名称或“项目里已经有”
决定复用；先验证隔离能力、生命周期、版本、容量、故障域、网络和删除语义。

- 关系型数据库可以优先评估复用服务器实例，但必须创建独立 Database/Schema、用户和 Secret。
- Redis/Valkey/Memcached 默认由同一解决方案内的业务服务共享，跨解决方案默认不复用。
- Broker、对象存储、搜索和向量库只有具备可靠逻辑租户、凭据、配额与清理边界时才复用。
- 平台可观测、Gateway、证书和受控 Provider 默认复用平台能力，只创建当前应用的业务资源。
- PVC 默认应用独占；一次性迁移、初始化和部署 Hook 不创建长期运行的空应用。

无法从可信工具确定现有依赖是否兼容时，保留候选并让用户选择，不能自行假定可用。

## 生成部署配置

只预填被仓库事实支持的非敏感值：

- 仓库、版本、源码目录、构建上下文、Dockerfile、构建和启动命令。
- 语言运行时、容器端口、健康检查路径、环境变量名称和依赖类型。
- 文档明确给出的最低资源或持久化要求。

以下值必须由可信平台资源或用户决定：项目空间、应用名与标识符、目标集群、镜像站、
域名、环境阶段、资源规格、Secret 值和数据保留策略。先用平台工具发现候选，并按根 Skill
直接索引的 `resource-resolution.md` 自动采用唯一有效资源；只有仍存在真实选择时才让用户
决定，不让用户手填不透明 ID。

需要一个服务的参数时使用 `resource_configuration`；跨多个服务且字段有依赖时使用
`wizard`。交互卡片应显示来源路径、默认值依据和可编辑推断。Secret 使用平台受控字段，
不得进入 `send_message` 模板、普通参数摘要或最终回复。

提交前使用 `change_review` 核对服务拆分、目标、构建路径、运行端口、依赖的新建/复用
决策、隔离单元、删除语义、持久化、迁移和公网暴露影响。核对卡片不是执行结果。

## 执行交付

1. 选择或创建目标项目空间，回读真实 ID 和当前用户角色。
2. 为每个服务创建或复用应用；名称相同不能证明是同一个目标应用。
3. 绑定可信 Git 账号、仓库和固定版本，创建或验证 Webhook 策略。
4. 创建构建变量、构建配置和源码部署配置；按依赖计划复用、绑定或使用模板/可信镜像创建依赖。
5. 按依赖顺序执行数据库/基础服务、后端、前端；可以并行的构建不必串行。
6. 每个源码服务触发 BuildRun，成功后核对制品引用和 Digest。
7. 使用实际制品创建 Release。需要迁移时按项目支持的安全方式在应用启动前或发布阶段执行，
   不得用聊天中的临时命令绕过平台审计。
8. 观察 Release、Rollout、Pod、Service、事件和健康探针；按需配置网关、DNS 和 TLS。

工具目录暂时缺少下一项写操作时，保留已确认的结构化配置并准确说明阻塞 operation；
不要退化成“请前往页面自行完成”，也不要生成虚假的部署进度。

## 失败恢复与验收

失败时先定位阶段，不要从头重复读取所有资源：

- 仓库读取：检查账号、权限、分支、子模块、目标文件和网络限制。
- 构建：检查上下文、忽略文件、依赖锁、运行时版本、多阶段产物和 Registry 推送。
- 初始化/迁移：检查数据库可达性、迁移版本、幂等性、锁和当前 schema 状态。
- 运行：检查镜像拉取、Secret/配置、端口、探针、退出码、卷权限和资源限制。
- 服务关系：检查 Service、Endpoint、内部地址、CORS、公开 Base URL 和依赖就绪。
- 网关：检查路由接纳、后端解析、DNS、证书和外部响应。

只重试瞬时故障。修正配置或源码后创建新的 BuildRun/Release，保留失败记录；需要回滚时
选择真实成功的历史制品或 revision。

源码交付完成至少需要以下证据：仓库绑定指向预期版本；每个源码服务 BuildRun 成功且
产生预期 Digest；依赖和迁移成功；Release 使用对应制品；工作负载与 Service 就绪；用户
要求的访问入口可以从外部访问。缺少任一必要证据时，只能报告进行中、失败或已阻塞。
