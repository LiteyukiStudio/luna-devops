# 站内消息盒子协议

本文只记录站内消息与待处理动作长期不变的业务边界。字段、枚举、路由和响应结构以 OpenAPI、
数据库模型与现行代码为事实源，避免在文档中维护第二份接口定义。

## 1. 对象边界

- `PlatformEvent` 是平台发生事实的不可变记录，不承载某个用户的已读、归档或决定状态。
- `NotificationDelivery` 记录邮件、Webhook 等外部渠道投递，不等同于站内消息。
- `InboxMessage` 是面向单个接收者的投影，独立保存已读与归档状态。
- `ActionRequest` 是需要用户作出结构化决定的请求，拥有独立状态、版本与审计链。

站内消息不是通知渠道的别名。同一平台事件可以投影为零到多条用户消息，也可以触发外部投递；
各投影失败或状态变化不得篡改原始事件。

## 2. 投影与展示

- 只有明确允许的事件类别、优先级、i18n key 和字段可以进入消息盒子，禁止把任意日志、异常、
  HTML 或第三方响应直接投影给用户。
- 标题、描述和操作文案由前端根据稳定 key 本地化；后端返回稳定 code、枚举和必要原始备注。
- 深链只能指向平台内受控路由，并在打开时重新校验登录状态、项目空间和资源权限。
- 已读、未读、归档和取消归档只属于接收者投影，与底层事件、外部投递和动作终态相互独立。
- 查询必须按当前用户隔离；平台管理员权限不自动意味着可以读取其他用户的私人消息。

## 3. 动作请求

- 决定只能由当前接收者对 `pending` 请求提交，并以行版本或等价 CAS 防止重复和并发覆盖。
- 执行前必须重新检查用户、登录 Session、角色、项目空间、目标资源、参数和当前业务不变式；消息
  中保存的旧上下文不能替代权威回读。
- 批准、拒绝、取消、过期和执行结果必须形成稳定终态与审计记录。重复请求应返回同一终态或明确
  冲突，不得重复产生副作用。
- 消息中的按钮不能携带任意 URL、HTTP 方法或请求体直接执行；所有动作必须映射到平台注册的
  业务操作，并继续经过 Handler/Service/RBAC、审批和审计。
- 涉及账单归属、Owner 转移或资源删除时，必须保持最后 Owner、余额、活动引用和不可逆操作确认等
  业务不变式，不能以消息确认绕过。

## 4. 实时与一致性

- PostgreSQL 是消息和动作状态的权威来源；SSE 只发送失效通知或可验证的增量，不维护第二份状态。
- 断线、序号缺口或订阅切换后必须重新读取权威列表；前端不得保留旧消息冒充当前状态。
- 消息创建、动作状态转换和必要审计应使用事务或可证明的幂等边界；外部副作用采用可重试任务时，
  必须保存幂等键与可观察终态。

## 5. 安全与可观测

- Secret、Token、Cookie、Authorization、完整请求体和第三方敏感内容不得进入消息正文、动作参数、
  日志、Trace 或 Metric。
- Trace 延续到消息投影、动作执行、数据库和异步任务；日志使用稳定事件名与关联 ID，Metric 只使用
  低基数状态和类别。
- 至少测试用户隔离、权限撤销、并发决定、重复提交、过期、执行失败、SSE 恢复、审计关联和敏感
  字段不泄漏。
